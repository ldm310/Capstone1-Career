# 역량 추출 엔진(계획 1/3) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** GitHub 계정 하나를 넣으면 main·develop(dev·develope 포함)에 남은 본인 줄을 squash·복사·대량 업로드까지 가려 정확하게 귀속하고, 기계 실행 기록만으로 기술별 LV와 내 STAT을 내는 수집·판정 엔진을 완성한다(CLI로 검증).

**Architecture:** 기존 `collector/`(Python)를 고친다. 귀속은 git blame 위에 세 겹을 더한다. ① squash commit을 PR 원본에 이어 붙이는 graft ② 복사 추적 ③ 대량 업로드 분류. 실행 근거는 「그 실행이 다룬 기술」 단위의 플래그로 바꿔 규칙 먼저 판정에 넣는다. 계획 2(분석 서버·단계별 화면)와 계획 3(팀 FE·BE 합치기)은 이 엔진의 함수와 DB를 그대로 쓴다.

**Tech Stack:** Python 3.13(collector/.venv), git CLI, GitHub REST(career-stat-bot 토큰), SQLite(store.py, user_version 4), anthropic SDK(Haiku 5.5), unittest.

**Spec:** `docs/superpowers/specs/2026-10-28-github-competency-design.md`(승인 2026-10-29). 계획과 함께 반드시 읽는다.

## Global Constraints

- 사용자 코드는 실행하지 않는다. 실행 증거는 GitHub·배포 플랫폼이 남긴 기록만 쓴다.
- Claude API는 이제부터 최대 $10. 모델은 Haiku 5.5(`claude-haiku-5-5`), 서비스 경로는 effort high·출력 한도 32K.
- GitHub 토큰은 `~/.config/career-stat/github.env`의 `GITHUB_TOKEN`(career-stat-bot)만 읽는다. 개인 gh 토큰으로 넘어가는 경로를 두지 않는다. 토큰은 HTTP 헤더로만 넘기고 URL·명령줄·로그·git 설정에 남기지 않는다.
- 분석은 동의 기록(`account` 표)이 있는 계정만 한다.
- 평가 대상은 main(기본 브랜치)·develop·dev·develope에 남아 있는 줄이다. 다른 ref(PR 원본, 내 브랜치)는 출처 확인에만 쓴다.
- 거짓 인정이 놓침보다 나쁘다. 확신이 없으면 「출처 불명」·「확인 필요」로 두고 내 줄로 세지 않는다.
- 재지 않은 값은 N/A. 측정 결과에는 코드 commit SHA와 수정 중 여부를 남긴다.
- `01-decisions/`~`05-memory/`는 고치지 않는다. 팀 레포에 push하지 않는다. 비밀값은 commit하지 않는다.
- 시험은 `cd collector && .venv/bin/python -X dev -m unittest test_engine test_store test_extract test_attribution test_evidence`로 돌린다. 네트워크를 쓰는 시험은 두지 않는다(GitHub API는 FakeApi로 대신한다).

## Review Focus

1. **PR이 수만 개인 레포**(예: vllm 원본, PR ref 44,146개): 필요한 PR ref만 받아야 한다. 모든 `refs/pull/*`를 받으면 몇 분씩 걸린다. → Task 5 `test_fetches_only_needed_pr_refs`
2. **레포 하나의 GitHub API 실패**(404·422·5xx·한도): 그 레포만 「미확인」이 되고 계정 전체는 계속돼야 한다. → Task 2 `test_api_error_isolates_one_repo`
3. **기본 브랜치가 main이 아니고 develop 계열이 dev인 레포, 빈 레포:** 브랜치를 빠뜨리거나 빈 레포를 실패로 세면 안 된다. → Task 2 `test_branch_set_includes_dev_aliases`, `test_empty_repo_is_not_failure`
4. **레포에 심은 `.mailmap`:** 남의 줄이 내 줄로 바뀌면 안 된다. → Task 3 `test_planted_mailmap_cannot_claim_lines`
5. **본인 줄이 전부 보류·제외된 계정:** 오류 없이 STAT이 「미확인」과 이유를 내야 한다. → Task 11 `test_all_lines_held_gives_unconfirmed_stat`

### Task 5: squash 되찾기(grafts.py)

**Files:**
- Create: `collector/grafts.py`
- Test: `collector/test_attribution.py` 클래스 `Squash`

**Interfaces:**
- Consumes: `gitenv.env`, `testkit.FakeApi`, `testkit.Repo`
- Produces:
  - `REPLACE_BASE = 'refs/career/replace/'`, `PR_REF = 'refs/career/pull/{n}'`
  - `@dataclass class GraftResult: grafted: dict[str, str]; unknown: dict[str, str]; co_authors: dict[str, list[str]]` — squash SHA → PR 머리 SHA / squash SHA → 이유 / squash SHA → 공동 작성자 이메일
  - `squash_like(path: Path, revs: list[str], env: dict) -> list[tuple[str, str]]` — (SHA, 제목). 부모 1개이고 committer 이메일이 `noreply@github.com`인 commit.
  - `build_grafts(path: Path, api, full: str, revs: list[str], wanted_prs: set[int] | None, env: dict) -> GraftResult` — API `GET /repos/{full}/commits/{sha}/pulls`에서 `merge_commit_sha == sha`이고 merged인 PR을 찾는다. `git fetch origin refs/pull/{n}/head:refs/career/pull/{n}` 뒤 `git replace --graft <squash> <squash 부모> <PR 머리>`를 REPLACE_BASE에 만든다(이 이름공간은 `gitenv.env(replace_base=REPLACE_BASE)`로만 보인다). 이어 붙인 뒤 새로 닿는 squash 모양 commit이 없을 때까지 되풀이한다(본 SHA는 다시 보지 않음).
  - rebase 판별: PR commit이 1개이고, 그 commit과 squash commit의 author 이메일·author 날짜가 같으면 graft하지 않는다(이미 같은 작성자).
