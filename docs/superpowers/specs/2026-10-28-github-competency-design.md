# GitHub URL → 내 역량 추출 설계(중간발표판)

- 상태: **승인 요청**. 사용자 결정과 빌더 검토(질문 8개)를 모두 반영했다(2026-10-29). 승인 전에는 이 문서를 근거로 기능 코드를 만들지 않는다.
- 중간발표 필수 범위(확정 2026-10-29): 역량 추출 + 단계별 화면 + **팀 FE·BE와 합치기까지**. 발표 화면은 캡처라서 시간보다 정확성이 우선이다. 발표 날짜는 미정.
- 진행: 설계 문서 승인 → 계획(writing-plans) → ① 역량 추출 검증 → ② 팀 FE·BE와 합치기(사용자가 정한 순서)
- 표기: **확정**(사용자가 정함) · **제안**(Claude 판단, 빌더가 바꿀 수 있음) · **미정**(나중에 정함) · **측정**(실제로 잰 값, 정확도 아님)
- 결정의 원본 기록: `HANDOFF.md` 「변경 기록」(2026-10-28~29). 지난 판본과 버린 안(B안 등)은 git 기록(`3d40868`)에 있다.

## 1. 무엇을, 왜

사용자가 서비스 화면에 **GitHub URL 하나**를 넣으면, 그 계정의 공개 레포에서 **main·develop에 남아 있는 본인 코드만** 골라 **기술별 LV(LV0~5)와 내 STAT**을 보여 준다. 결과마다 근거(레포·commit·파일·줄·실행 기록)를 함께 보여 준다. 교수님 피드백(「LLM에 던지지 말고 근거와 규칙으로 평가했음을 보여라」)과 「거짓 인정이 놓침보다 나쁘다(채용 담당자가 본다)」가 설계의 기준이다.

서비스는 **한 번에 사용자 1명**을 분석한다. 받은 10명(본인 ldm310 + 동의한 지인 9명)은 추출이 얼마나 잘 되는지, 얼마나 걸리는지 보려는 시험 데이터다(확정 2026-10-29).

## 2. 목표 · 하지 않을 것 · 실패로 보는 것

**목표(확정)**
- G1. URL 하나로 그 계정의 공개 레포를 빠짐없이 찾는다(소유, 멤버, 본인 commit·PR이 있는 남의 레포).
- G2. 레포마다 main(기본 브랜치)과 develop(dev, develope 포함)의 코드만 평가한다.
- G3. 팀원이 내 코드를 가져가 고친 뒤 올려도(일반 병합·rebase·squash·같은 레포 안 복사) 남아 있는 내 줄은 내 몫, 팀원이 고친 줄은 팀원 몫으로 잡는다.
- G4. 정확성·신뢰성 95%를 목표로 하고, 잰 값만 말한다(재지 않은 값은 N/A).
- G5. 정확성이 속도보다 먼저다(확정 2026-10-29). 결과는 단계별로 보여 주고, 아직 계산 중인 값(squash 되찾기, 대량 업로드 판정, LV)은 「계산 중」으로 표시한다. 레포가 많으면 오래 걸려도 된다. 「5분 이내」는 강제 목표가 아니고, 시간은 재서 보고만 한다.

**하지 않을 것(이번 범위 밖)**
- PDF·.md 입력, 공고 적합도, 메타인지 리포트, 비공개 레포
- 다른 사람이 복사해 간 코드의 자동 탐색(「본인이 출처 지정 → 기계 검증」은 다음 단계)
- 외부 원본 조회(GitHub 코드 검색)로 남의 코드 확정(다음 단계)

**실패로 보는 것**
- 남의 코드를 내 줄로 세는 것(거짓 인정). 확신이 없으면 「출처 불명」·「확인 필요」로 두고 세지 않는다.
- 재지 않은 정확도를 말하는 것
- 우리 서버가 사용자 코드를 실행하는 것(읽고 분석만 한다)

## 3. 제약

- 사용자 코드는 실행하지 않는다. 실행 증거는 GitHub·배포 플랫폼이 남긴 기록만 쓴다.
- Claude API는 이제부터 **최대 $10**(확정 2026-10-29). 모델은 Haiku 5.5(`claude-haiku-5-5`).
- GitHub 토큰은 서비스 전용 계정 **career-stat-bot**의 토큰(scope 없음, 공개 읽기, 시간당 5,000회)을 `~/.config/career-stat/github.env`에서 읽는다. 개인 gh 토큰으로 넘어가는 경로는 두지 않는다.
- 분석은 동의 기록(`account` 표)이 있는 계정만 한다.
- `01-decisions/`~`05-memory/`는 고치지 않는다. 비밀값은 commit하지 않는다. 팀 레포에는 push하지 않는다(fe-preview는 push 주소를 막아 둠).
- 이 폴더는 로컬 git 저장소다(원격 없음). 측정할 때마다 코드 commit SHA와 수정 중 여부를 결과에 남긴다.

## 4. 전체 흐름

```
URL 입력(Next.js) ─▶ 분석 서버(FastAPI, 127.0.0.1)에 작업 등록
  1. 동의 확인: account 표에 없거나 철회됐으면 거절
  2. 레포 찾기(GitHub API) ──────────────▶ [첫 화면] 레포 목록
  3. 레포별 병렬(4개 안팎): clone/fetch → 내 줄 계산 → 기술 찾기 ──▶ [첫 화면] 내 줄·기술 목록(레포가 끝나는 대로)
  4. 실행 근거 모으기(GitHub API): Actions·check run·배포 기록
  5. 기술 × 레포 × 브랜치마다 판정: 규칙 먼저 → 필요할 때만 LLM ─▶ [채움] LV가 끝나는 대로
  6. 기술 LV(브랜치·레포 중 최고) → 내 STAT ────────────────▶ [완료] STAT, 막힌 이유, 다음에 할 일(④ 안내)
```

## 5. 부분별 설계

### 5.1 수집(extract.py 고침)
- **레포 범위:** 소유 + 멤버 + 본인 commit·PR 검색. 지금 계정당 30개 상한이 소유 레포부터 채워 팀 레포를 빠뜨린다(sangwon5579 팀 레포 8개 누락, R1 위반). 정확성이 먼저이므로 **상한 없이 공개 레포를 모두 분석**한다. 본인 commit이 있는 레포를 먼저 처리해 화면에 먼저 채운다. **(Claude 판단, G5에 따름)**
- **브랜치:** 기본 브랜치, main(없으면 master), develop, dev, develope(확정 2026-10-29).
- **clone:**
  - checkout 없는 clone(`--no-checkout`)으로 받는다. 이렇게 해야 레포의 `.mailmap`이 작성자를 바꾸지 못한다. checkout clone에서는 설정으로도 막지 못했다(검토에서 10/10 재현).
  - 큰 파일(512KB 초과)은 받지 않는 부분 clone(`--filter=blob:limit=512k`)으로 받는다. 300MB를 넘는 레포도 코드는 평가한다(지금은 Unity 레포 2개가 통째로 빠짐). 512KB를 넘는 파일은 지금도 분석하지 않으므로 결과는 같다(제안).
  - 토큰은 HTTP 헤더로만 넘기고, URL·명령줄·로그·git 설정에는 남기지 않는다.
- **신원:** 내 commit은 GitHub API의 계정 연결(author.login)과 연결된 이메일로 판정한다. blame이 보여 주는 이름이 아니라 commit SHA로 찾은 원래 이메일(`%ae`)을 쓴다. 이름만 같은 commit은 세지 않는다(지금과 같음).
- **API:**
  - ETag 조건부 요청으로 응답을 캐시한다(304는 한도에 안 셈).
  - 동시 요청은 적게 하고, 한도 초과(retry-after, x-ratelimit-reset)와 5xx는 기다렸다 다시 한다.
  - 레포 하나의 API 오류는 그 레포만 「미확인」으로 두고 계정 전체를 멈추지 않는다.
  - 크기 때문에 건너뛴 레포는 실패로 세지 않는다.
- **동시성:** 같은 레포 캐시는 한 번에 한 작업만 쓴다(잠금).

### 5.2 내 줄 귀속(blame)
1. **기본:** 평가 commit에서 git blame(`-w`)으로 줄마다 마지막 작성자를 본다. 결과가 정해진 파일은 줄 수만 세는 빠른 길을 쓴다(10-28 구현, 실제 레포 128건이 전체 blame과 같음).
2. **squash 되찾기(확정, 중간발표 범위)**
   - 대상: main·develop의 commit 중 「부모 1개 + GitHub가 만든 commit(committer web-flow) + 어떤 PR의 merge_commit_sha와 일치」인 것만 squash로 본다.
     - PR과의 일치는 GitHub의 「commit에 연결된 PR」 API로 확인한다.
     - 웹 화면에서 직접 고치거나 올린 commit(「Create …」「Update …」「Add files via upload」 등, 연결된 PR 없음)은 squash가 아니라 작성자 그대로인 직접 commit으로 본다.
     - fail closed는 두 경우에만 한다. 제목에 「(#번호)」가 있는데 PR 기록을 못 찾은 경우, 그리고 PR 조회 API가 실패한 경우다.
     - 이유: 10명의 본인 commit 2,587개 중 부모 1개·web-flow가 715개였고, 그중 「(#번호)」 squash 제목은 70개, 웹 편집·업로드형은 578개였다(제목 패턴으로 센 값). 웹 편집까지 막으면 8명의 줄 약 3.2만이 빠진다. **(Claude 판단, 빌더 검토 반영)**
   - 방법: 그 PR의 원본(`refs/pull/N/head`)을 받아, 로컬에서만 squash commit에 PR 머리를 부모로 이어 붙인다(`git replace --graft`). 그 뒤 blame하면 줄마다 PR 안의 원래 작성자가 나온다. 여러 번 squash된 것(develop → main)도 끝까지 잇고, 순환은 막는다.
   - rebase 판별: patch-id만으로 정하지 않고, 작성자·작성 시각까지 맞을 때만 rebase로 본다.
   - **빠른 길(history)을 포함한 모든 git 호출이 같은 graft를 본다.** 안 그러면 squash로 들어온 파일이 PR 연 사람에게 통째로 간다(합성 시험에서 정답 10줄이 20줄로 잡힘).
   - **fail closed:** PR 기록과 맞추지 못한 squash 모양 commit은 내 것이어도 세지 않고 「출처 불명」으로 둔다. PR 원본 보관 기간은 공식 문서에 없다. 기록이 있으면 쓰고, 없으면 확정하지 않는다.
   - GitHub가 squash commit에 넣는 공동 작성자(`Co-authored-by`)는 「참여 신호」로만 보여 준다. 어느 줄인지는 알 수 없어서 줄 귀속에는 쓰지 않는다.
   - PR 조회는 내 commit이나 내가 연 PR이 있는 레포에서만 하고, 필요한 PR ref만 받는다.
3. **같은 레포 안 복사(확정, 중간발표 범위):** git blame의 복사 추적(`-C`)으로 다른 파일에서 옮겨 온 줄을 원래 작성자에게 돌린다. 전체에 쓰면 6.5배 느려져서 의심 파일에만 쓴다. 의심 파일은 같은 commit에서 다른 파일이 크게 줄어든 경우 등이다(빌더 판단).
   - 범위: main·develop 이력 안(graft로 이은 PR 포함)에서 다른 파일로 옮긴 코드만 잡는다. 팀원이 **병합되지 않은 내 브랜치**에서 복사해 새 commit으로 올린 코드는 `-C`로 잡히지 않는다. 중간발표에서는 놓침으로 두고, 발표에서도 그렇게 말한다. 「본인이 출처 지정 → 기계 검증」(다음 단계)이 이 경우를 다룬다(사용자 결정 2026-10-29에 따름).
4. **대량 업로드(확정)**
   - **뺌:** 한 commit에 코드 파일 1,000개 이상 추가, 또는 남의 표지가 있는 파일. 표지는 SPDX, Copyright(남의 이름), 「Licensing Information」, 「Permission is hereby granted」, 「Licensed under」, 「All rights reserved」, @generated, 의존성 폴더(site-packages, _vendor, Windows 가상환경 Lib/·Scripts/, pyvenv.cfg)다. 그 commit이 들여온 줄만 빼고, 뒤에 본인이 고친 줄은 그대로 둔다.
   - **보류(「확인 필요」):** 아래 셋 중 하나면 보류한다(확정 2026-10-29).
     - 한 commit에 코드 파일 200개 이상을 처음 올린 경우
     - starter·skeleton·template 같은 폴더 이름: 신호만으로 보류
     - 「Initial commit」「upload project」 같은 commit 메시지: 그 commit이 코드 파일 100개 이상일 때만 보류. 흔한 메시지라 단독으로는 쓰지 않는다(본인 commit 중 이런 메시지 24개 가운데 23개가 50파일 미만이었다).
     - 보류된 줄은 화면에 따로 보여 주고, 확정 LV의 근거와 정확도 계산에 쓰지 않는다.
     - 사용자가 화면에서 「내 코드 맞음」을 누르면 인정하되, 「본인 신고」 등급으로 표시한다.
   - **그대로:** 나머지는 그대로 센다.
   - **이유:** 파일 200개 이상을 올린 commit 5개 중 4개가 남의 코드였다(리눅스 커널, OS161, 가상환경, Berkeley Pacman 과제 틀). 숫자는 이 10명에서 정한 값이라 제안이다.
   - LLM에게 판단시키지 않는다. 같은 commit을 두고 기술마다 다르게 판단했기 때문이다.
5. **경로 필터 보강:** 빌드 결과물(.exe, .dll, .obj, .pdb 등)과 데이터·생성 파일을 뺀다. 데이터·생성 파일은 큰 SQL 덤프와 minified 파일(줄 평균 길이로 판별)이고, 직접 쓴 schema.sql은 남긴다. 이 필터와 대량 업로드 규칙은 줄 세기·기술 찾기 **전에** 적용한다(sweetholly 365초의 원인 제거).
6. **결과 단위:** 줄마다 귀속 경로를 남긴다. 경로는 직접 blame / squash로 되찾음 / 같은 레포 복사 / 본인 신고 / 보류 / 출처 불명이다. 화면과 정확도 측정이 이 구분을 쓴다.

### 5.3 실행 근거
- **원칙(확정):** 기계(GitHub·배포 플랫폼)가 그 코드 버전으로 실제로 돌린 기록만 인정한다. 사용자가 올린 결과 파일은 인정하지 않는다(B안 취소).
- **기록 종류를 나눈다.**
  - 테스트·빌드 CI(Actions, check run)
  - 배포: Vercel 등 플랫폼 봇. 사람이 남긴 status는 제외한다.
  - GitHub Pages
  - 자동화(라벨·파일 이동 등): 실행 근거가 아니다.
- **GitHub Pages(확정):** HTML·CSS 기술에만 실행 근거로 인정하고, L0-04는 미확인으로 둔다.
- **실행이 다룬 기술에만(확정 2026-10-29):** CI·배포 기록은 그 실행이 실제로 다룬 기술에만 근거가 된다. workflow 명령(예: `pytest`, `npm test`, `./gradlew test`)과 배포 대상을 기술에 대응시키는 표로 가려낸다. 프런트 빌드 하나로 같은 commit의 Python이 LV0을 받는 일을 막는다.
- **L0-04(의도한 출력, 확정 2026-10-29):** 테스트를 돌려 성공한 기록은 인정한다(테스트가 기대한 결과를 확인하므로). 빌드·배포만 한 성공은 「프로그램이 끝났다」일 뿐이라 L0-04 근거가 아니다. 이 경우 Vercel 화면 내용이나 ④ 검증 결과가 있어야 한다.
- **같은 버전(확정):** 코드 파일만의 해시가 같으면(문서·workflow 변경 무시) 다른 commit(바로 전 commit, PR 머리)의 실행 기록도 인정한다.
- **거짓 성공 막기:** 같은 commit의 workflow에 `continue-on-error`나 `|| true`가 있으면 그 성공을 근거로 쓰지 않는다.
- **오래된 commit:** Actions 로그는 최대 90일 뒤 지워지고, 다시 실행은 30일까지만 된다(공식 문서). 성공 기록은 남으므로 L0-03 근거로 인정한다. L0-04(의도한 출력)에 필요한 출력이 없으면 ④로 다시 돌리게 안내한다. 로그 API는 쓰지 않는다(scope 없는 토큰으로 403, 지금 데이터에서 바꿀 LV 0건).
- **④ 검증 workflow 안내:** 실행 기록이 없는 레포에 스택별(Python·Node·Java) GitHub Actions 파일과 「추가하기」 링크를 준다. 링크는 GitHub 새 파일 화면을 미리 채운 것이다.
  - 이 workflow는 테스트·실행 결과를 **check run 출력**(최대 65,535자, API로 읽힘)으로 남긴다. job summary는 API로 읽는 공식 경로가 없어서 쓰지 않는다.
  - 파일 해시가 우리 템플릿과 같을 때만 「표준 검증」으로 표시하고, 분석할 때 출력 요약을 DB에 저장한다.
  - GitHub가 실행하므로 우리 서버는 실행하지 않는다(공개 레포는 무료).
- **배포 화면:** Vercel의 그 commit 전용 주소는 HTML과 상태 코드만 읽는다. 브라우저 렌더링(JS 실행)은 하지 않는다. 로그인으로 막혀 있으면 미확인으로 둔다.

### 5.4 판정(engine.py)
- 기준표 31개 조건과 LV0~5 누적 규칙은 그대로다(확정).
- **평가 commit(확정):**
  - main·develop(dev, develope 포함)의 최신 commit을 각각 판정하고, 기술 LV는 높은 쪽으로 한다.
  - 한 판정 안에서는 같은 버전의 코드와 실행 기록만 쓰고 섞지 않는다.
  - 화면에 LV마다 브랜치와 SHA를 보여 준다. 높은 쪽 규칙으로 정해진 건수를 따로 센다.
- **규칙 먼저:** LLM 답과 상관없이 LV가 규칙으로 이미 정해지면 LLM을 부르지 않는다. 경우는 둘이다. ① 그 기술의 실행 근거가 없을 때(지금과 같음, 10명 기준 239건 중 230건) ② 실행 근거는 있지만 L0-04를 규칙상 충족할 수 없을 때(빌드·배포만 있고 출력 없음, Pages). 이때 조건 해석 칸은 비어 있다고 화면에 밝힌다. **(Claude 판단, 2·3번 결정에 따름)**
- **LLM 조건**
  - Haiku 5.5, effort high, 출력 한도 32K를 유지한다(서비스 경로).
  - 프롬프트는 10만 토큰 아래로 맞춘다. 제안: 파일 전체 대신 본인 줄 주변을 보여 준다. 10만을 넘으면 단가가 5배이고, 비용의 77%가 이 구간에서 나왔다.
  - 출력이 잘리면 effort medium으로 1번만 다시 한다(제안).
- **예산:** DB 장부에 누적하고, 호출 전에 최악 비용을 잡아 둔다. 병렬로 불러도 $10 상한을 넘지 않게 한다.

### 5.5 화면(fe-preview → 팀 FE)
- URL 입력 → 진행 표시: 레포 목록 → 내 줄·기술 목록(레포가 끝나는 대로) → LV(판정이 끝나는 대로) → STAT
- LV마다 표시할 것: 브랜치·SHA, 실행 근거 종류(CI / 배포 / Pages / 없음), 근거 등급, 막힌 조건
- 보류된 대량 업로드 목록과 「내 코드 맞음」 버튼

- 실행 기록이 없는 레포: ④ 안내 버튼
- 계산 중인 값은 「계산 중」으로 표시한다(squash 되찾기, 대량 업로드 판정, LV).

### 5.6 분석 서버(확정: 따로 둔다)
- FastAPI, `127.0.0.1`에서만 연다. Next.js 서버가 대신 부른다(브라우저에서 직접 접근하지 않음).
- 작업 상태는 DB 표에 저장해 서버를 다시 켜도 남게 한다. 별도 작업자 프로세스가 한 번에 1~2계정을 처리한다.
- API(제안): 작업 등록(URL), 진행 조회(단계별 결과), 결과 조회, 「내 코드 맞음」 기록. Next.js는 2~3초마다 조회한다.
- 저장: 중간발표까지 SQLite(WAL, busy_timeout). PostgreSQL `eval` 스키마(`collector/db/schema.sql`)는 문법만 확인했고 실제 생성은 안 했다(미정, 팀과 결정).
- 팀 연동(사용자 순서 2번)
  - 팀 레포의 최신 feature/FE(12e5439)와 feature/BE(7541081, 인계 사본보다 새것)를 받아 읽은 뒤 붙인다.
  - BE(Spring)가 분석 결과를 어떻게 받을지(분석 서버 API 호출 / 같은 DB)는 BE 코드를 읽고 정한다(미정, 선영과 상의).
  - 팀에 「Python 분석 서버를 둔다」고 알린다. 그림 9 갱신은 미정이다.

## 6. 고른 방법과 이유(Approaches)

| 주제 | 고른 것 | 버린 것과 이유 |
|---|---|---|
| squash | PR 원본 기록으로 되찾기 + 확인 못 하면 세지 않기 | 그대로 두기: 놓침과 거짓 인정이 함께 생긴다(지금은 squash 줄을 PR 연 사람에게 통째로 줌) |
| 복사 | 같은 레포 안 복사 추적(의심 파일) | 자동 내용 대조: 같은 튜토리얼 코드도 걸려 오판 위험(마지막으로 미룸). 본인 출처 지정 검증은 다음 단계 |
| 대량 업로드 | 3단계 + 수업 틀 신호 + 본인 확인 버튼 | 1,000 기준만: Pacman 틀(205파일)을 놓침. LLM 판단: 일관성 없음 |
| LV0 실행 근거 | 기계 기록만(Actions·배포·같은 코드) + ④ 안내 | B안(결과 파일 인정): 근거 확실성이 낮아 사용자가 취소 |
| 평가 commit | 브랜치별 판정, 높은 쪽 | 한쪽만: Ieum main 140줄 대 develop 8,715줄처럼 일이 빠짐 |
| 로그 | 쓰지 않음 | 권한을 넓혀도 지금 바뀌는 LV 0건, 최소 권한 원칙 |
| 분석 서버 | FastAPI 별도 서버 | Next.js가 Python을 직접 실행: 프로세스 관리가 어렵고 팀 BE와 경계가 없음. TypeScript 이식: 검증된 Python 코드를 다시 검증해야 함 |
