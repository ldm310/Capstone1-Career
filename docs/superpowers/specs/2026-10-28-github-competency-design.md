# GitHub URL → 내 역량 추출 설계

- 상태: **작성 중(요구 정리 단계)**. 아직 승인 전이라 이 문서를 근거로 기능 코드를 만들지 않는다.
- 진행 방식: superpowers brainstorming → 이 설계 문서 → 사용자 승인 → 계획(writing-plans) → 개발(테스트 먼저)
- 표기: **확정**(사용자가 정함) · **제안**(Claude 제안, 승인 전) · **미정**(정해야 함) · **측정**(실제로 잰 값)
- 결정의 원본 기록은 `HANDOFF.md` 「변경 기록」이다. 이 문서는 그중 이번 목표에 필요한 것만 모은다.

## 1. 무엇을, 왜

- 사용자가 서비스 화면에 **GitHub URL 하나**를 넣으면, 그 계정의 공개 레포를 모두 찾는다. 레포마다 **main·develop**에서 **본인이 쓴 부분만** 골라 **기술별 역량(LV0~5)과 내 STAT**을 뽑는다. (확정)
- 중간발표까지의 목표다. 교수님 피드백(근거와 규칙으로 평가했음을 보여 줄 것)에 맞춰, 결과마다 근거(레포·commit·파일·줄)를 보여 준다. (확정)
- 입력은 GitHub URL만 쓴다. PDF·.md는 나중에 한다. (확정, 2026-10-28)

## 4. 하지 않을 것 / 실패로 보는 것

- 남의 코드를 내 몫으로 잡는 것(거짓 인정). 채용 담당자가 보는 결과라서, 내 줄을 놓치는 것보다 나쁘다. (제안: 근거가 약하면 「출처 불명」으로 두고 세지 않는다)
- 재지 않은 정확도를 쓰는 것. 측정하지 않은 값은 N/A로 둔다. (CLAUDE.md)
- 사용자 코드를 실행하는 것. 읽고 분석만 한다. (CLAUDE.md)
- 유료 자원을 새로 쓰는 것. Claude API는 사용자가 정한 예외(남은 크레딧 약 $13.5, 11월 중순까지)이고 Haiku 5.5를 쓴다. (확정)

  - 수집 시간의 대부분은 GitHub API 호출과 clone을 차례로 하는 데 쓴다. 병렬로 바꾸면 줄어든다(계획에 넣음).

**받은 계정 조사(읽기 전용 API, 2026-10-28)**
- 병합된 PR 표본 83개 중 일반 병합(merge commit)이 81개, squash 0개, 판별 불가 2개였다. 이 사람들은 주로 일반 병합을 쓴다. 복사는 API로 셀 수 없다.
- GitHub Actions 실행 기록이 있는 레포는 확인한 101개 중 10개였다. 지금 규칙(같은 commit의 성공한 실행 기록이 있어야 LV0)으로는 대부분 미확인이 된다.

**공식 문서로 확인한 것**
- squash 병합 commit의 작성자가 누구로 남는지는 문서에 명시가 없다. 2019년 변경 공지는 PR 안 commit 작성자들을 squash commit의 공동 작성자(`Co-authored-by`)로 넣는다고 한다.
- PR 원본은 `git fetch origin pull/<번호>/head`로 받을 수 있다. 보관 기간은 문서에 없다.
- 「commit에 연결된 PR」 API는 그 commit을 기본 브랜치에 넣은 병합 PR을 돌려준다. PR의 commit 목록은 최대 250개다.
- 토큰 없이 하는 HTTPS clone에도 2025-05부터 한도가 걸린다. clone도 토큰으로 해야 안정적이다.

squash·복사 되찾기 방법 2~3개를 비교해 사용자가 고른다. **준비 중**(공식 문서 확인·계정 조사 완료, 설계안 3개와 평가 진행 중).

## 6-1. 실행 기록이 없을 때 LV0 근거 — B안(사용자가 취소함, 2026-10-28)

> **취소:** 트레이드오프(근거 확실성이 낮아짐)를 보고 사용자가 B를 취소했다. 기존 원칙(기계가 그 버전으로 실제로 돌린 기록만 인정)을 유지하고, 그 안에서 부족한 점을 보강한다(6-2장). 아래는 기록으로만 남긴다.

- **왜:** GitHub Actions 기록이 있는 레포가 적어서(조사한 101개 중 10개), 지금 규칙으로는 거의 모든 기술이 LV0부터 미확인이 된다.
- **고른 방법(사용자 결정 2026-10-28):** B. 기준표는 그대로 두고 L0-03 근거를 넓힌다. 같은 commit에 들어 있는 실행 결과 파일을 근거로 인정하고 「근거 등급 낮음」으로 표시한다. 기준표 L0-03의 「버전이 연결된 로그·출력·테스트 결과·분석 산출물」과 맞는다.
- **버린 방법:** A(코드만 있으면 LV0)는 확정 결정 2번과 기준표 원문(「코드는 있으나 실행 가능한지는 확인되지 않음」 불인정)에 어긋난다. C(LV0 후보로만 표시)는 LV를 하나도 인정하지 못한다.
- **조사(10명, 2026-10-28, `collector/out/gold-collect/scan_outputs.py`):** 평가 commit 195개 중 22개에 후보가 있었다.
  - 실행 출력이 있는 노트북 49개(본인 줄 37): lsy341·sangwon5579·scottXchoo
  - 로그 47개(본인 줄 43): sangwon5579·scottXchoo·sweetholly·tragicoding
  - 결과 그림 31개, 결과 데이터 1개: tragicoding
  - 테스트 결과 파일(JUnit XML)은 0개
  - 즉 B로 LV0 근거가 생길 수 있는 사람은 10명 중 5명이다. 나머지 5명은 실행 기록도 결과 파일도 없어 미확인으로 남는다(기준표대로면 맞는 결과).
- **정해서 만드는 것(내 판단, 확인 부탁)**
  1. **적용 조건:** L0-03(수행 결과 존재)과 L0-04(결과가 목적에 부합). LV0을 인정하려면 둘 다 필요하기 때문이다. L1-04·L2-04 등 나머지 실행 기록형은 그대로 GitHub Actions만 인정한다.
  2. **인정하는 파일(평가 commit에 있는 것만):** 실행 출력이 저장된 노트북, 테스트 결과 파일, 로그(.log·.out), 결과 폴더(results·output·figures·plots·logs·reports)의 데이터·그림.
  3. **LLM에게 보여 주기:** 후보 목록을 FACTS에 적고, 내용 일부를 함께 보여 준다. 노트북은 글자 출력만, 로그는 끝부분, 데이터는 앞부분을 보여 주고, 길이 상한을 둔다. 지금은 노트북이 판정 자료에 아예 안 들어간다.
  4. **규칙 검사:** 충족(met)이면 그 결과 파일이나 FACTS의 해당 줄을 그대로 인용해야 한다. 아니면 근거 부족으로 내린다(지금 규칙과 같은 방식).
  5. **근거 등급:** 결과 파일로 충족한 조건은 「근거 등급 낮음」, GitHub Actions로 충족한 조건은 지금처럼 표시한다. 등급은 DB에 칸을 더해 남긴다(정답 세트에서 등급별 정확도를 따로 재기 위해서).
  6. **LLM 호출:** 실행 기록도 결과 파일도 없을 때만 LLM을 건너뛴다. 결과 파일이 있으면 부른다. 조사 기준으로 대상은 수십 건이고, Haiku로 몇 달러 안쪽이다(추정).
  7. **버전 연결:** 노트북은 코드와 출력이 한 파일이라 같은 버전이다. 다른 결과 파일은 같은 commit에 있다는 것만 확인하고, 그 결과가 이 코드에서 나왔는지는 LLM이 판단한다. 이 한계 때문에 등급이 「낮음」이다.
- **하지 않는 것:** 사용자 코드를 실행해서 결과를 만들지 않는다. 결과 파일이 없는 레포를 LV0으로 올리지 않는다.
- **바뀌는 곳:** `engine.py`(규칙·프롬프트, 버전 올림), `assess.py`(FACTS·자료·LLM 건너뛰기 조건), `store.py`·`schema.sql`(등급 칸, DB 버전 4, 자동 백업), `export_stat.py`·FE 미리보기(등급 표시), 시험

## 6-2. 실행 근거 보강 — 안 1(사용자 결정 2026-10-28)

원칙은 그대로다. 기계(GitHub·배포 플랫폼)가 그 코드 버전으로 실제로 돌린 기록만 인정하고, 우리 서버는 코드를 실행하지 않는다. 그 안에서 도구 4개를 더한다.

| # | 도구 | 하는 일 | 10명 조사 |
|---|---|---|---|
| ① | 배포 기록 수집 | 배포 플랫폼 봇(Vercel 등)이 그 commit을 빌드·배포해 성공한 기록을 인정. 사람이 남긴 상태 표시는 제외 | Vercel 5건 |
| ② | 같은 코드 실행 찾기 | 다른 commit(PR 등)의 실행이라도 코드 트리 해시가 평가 commit과 같으면 같은 버전으로 인정 | 1건 |
| ③ | 실행 출력 읽기 | Actions 로그 끝부분, 그 commit 전용 배포 주소의 첫 화면을 LLM에게 보여 줘 L0-04 판단 | 위 12건 |
| ④ | 검증 workflow 안내 | 기록이 없는 레포에 스택별 GitHub Actions 파일과 「추가하기」 링크를 줌. GitHub가 실행 | 기록이 없는 3명 |

**오래된 commit(공식 문서와 직접 확인, 2026-10-28)**
- 공개 레포의 Actions 로그는 최대 90일 뒤 GitHub가 지운다. 다시 실행은 첫 실행 후 30일까지만, 쓰기 권한자만 할 수 있다.
- 직접 확인: 181일·348일 전 실행은 「성공」과 job 이름만 남고 step 이름과 로그는 없었다.
- 그래서 지워진 로그는 누구도 되살릴 수 없다. 대신 다음처럼 한다.
  - L0-03(실행 결과 있음): 성공 기록은 오래돼도 남으므로 그대로 인정한다.
  - L0-04(의도한 출력): 로그가 지워졌으면 ④로 지금 다시 돌리게 안내한다. 코드를 바꾸지 않는 commit을 올리면 GitHub가 같은 코드를 새로 실행하고, ②로 같은 버전임을 확인한다.
  - 앞으로는 분석할 때 출력 요약을 DB에 저장한다(시각·해시 포함). ④ workflow는 출력을 GitHub check 요약에 남겨서, 90일이 지나도 다시 볼 수 있게 한다(제안, 보관 기간 확인 필요).
- 추가 제약: Actions 로그 API는 지금 토큰(scope 없음)으로는 남의 공개 레포에서 403 「Must have admin rights」가 났다. `repo` 권한이 있는 gh 토큰은 받아졌다. 어떤 권한까지 줄지 정해야 한다(미정).

### 1. squash·복사 되찾기 — 「PR 기록 핵심 + 확신 등급 표시」
- 추천(중간발표 범위): GitHub에 남은 PR 원본(refs/pull/N/head)에 squash commit을 로컬에서만 이어 붙여(git replace --graft) blame한다. 여러 번 squash된 것도 끝까지 잇고, 순환은 막는다. rebase인지 squash인지는 patch-id만이 아니라 작성자·시각까지 맞춰 본다.
- 꼭 함께 고칠 것(검토 공통 필수):
  - PR 기록으로 확인 못 한 squash 모양 commit은 내 것이어도 세지 않는다(fail closed).
  - 신원은 blame에 찍힌 이름이 아니라 commit의 원래 이메일로 본다. 캐시를 checkout 없는 clone으로 다시 받아 .mailmap을 막는다(checkout clone에서는 설정으로도 못 막았다).
  - 빠른 blame 길도 graft를 보게 한다. 빠지면 합성 시험에서 정답 10줄이 20줄로 잡혔다.
  - 내 commit이나 내가 연 PR이 있는 레포만 PR을 조회한다. API 오류는 그 레포만 미확인으로 두고 계정 전체를 멈추지 않는다.
- 미룸: 복사 되찾기와 역방향 검사는 서버 시각 증거가 더 필요해 중간발표 뒤로 미룬다. 그동안은 「출처 불명」으로 둔다. 발표에서는 「R4는 squash만 충족, 복사는 일부」라고 말한다.
- 이유: (1) 지금 수집기는 squash commit의 줄을 PR을 연 사람에게 통째로 준다. 그래서 팀원 줄까지 내 줄로 센다(합성 시험 40줄 중 5줄 거짓). 즉 squash 처리는 놓친 줄을 찾는 일이면서 거짓 인정을 줄이는 일이다. (2) R5가 「확정한 결과」 기준이라, 확인 못 한 줄을 빼는 것이 정확도를 지키는 장치다.
- 주의: PR 원본 보관 기간은 공식 문서에 없다. 「기록이 있으면 쓰고, 없으면 확정하지 않는다」로 말한다. 일정은 6~7일 추정보다 늘어난다(다시 추정).

### 2. 대량 업로드 — 3단계(제안 숫자)
- 확실(뺀다): 한 commit에 코드 파일 1,000개 이상 추가, 또는 외부 표지가 있는 파일. 표지는 SPDX·Copyright·「Licensing Information」·「Permission is hereby granted」·「Licensed under」·「All rights reserved」·@generated, 의존성 폴더(site-packages, _vendor, Windows 가상환경 Lib/·Scripts/, pyvenv.cfg)다. 그 commit이 들여온 줄만 빼고, 뒤에 본인이 고친 줄은 blame상 뒤 commit이라 그대로 남긴다.
- 의심(보여 주되 확정 LV의 근거로 쓰지 않음): 한 commit에 코드 파일 200개 이상을 처음 올린 경우. 주인이 확인해 주면 인정한다(사람 검토).
- 나머지는 정상이다. 데이터·생성 파일(큰 SQL 덤프, minified)은 코드 줄에서 빼되, 직접 쓴 schema.sql은 남긴다.
- 이유(데이터): 파일 200개 이상을 올린 commit 5개 중 4개가 남의 코드였다(리눅스 커널, OS161, 가상환경, Berkeley Pacman 과제 틀). 1,000 기준만으로는 2개만 잡는다. Pacman 틀(205파일)은 지금 본인 줄 11,637줄로 잡혀 있는데, 학생이 직접 쓴 것은 그 뒤 +269줄뿐이다.
- 대가: 자기 프로젝트를 한 번에 200파일 넘게 올린 학생(예: Sierra 227파일)은 확인 전까지 보류된다. 거짓 인정이 놓침보다 나쁘다는 기준에 맞춘 선택이다. 숫자는 이 10명에서 정한 값이라 새 계정으로 다시 확인하고, 정답 세트에 「외부 코드」 라벨을 넣어 잰다.
- 덤: 이 필터를 줄 세기와 기술 찾기 전에 적용하면 sweetholly의 365초도 준다.

### 4. 평가 commit — main·develop 최신을 각각 판정, 높은 쪽(보완)

### 5. 정답 세트 — 지표를 먼저 고정하고, LV는 「m/n + 구간」으로만
- 판정 전에 지표를 고정한다.
  - 내 줄 정밀도: 줄이 아니라 덩어리(hunk) 단위로, 경로별(직접 blame, squash로 되찾음, 대량 업로드, 이름만 일치, 팀원 몫 대조군)로 층을 나눠 뽑는다. 한 층에서 59개를 오류 없이 맞혀야 단측 95% 하한(Clopper-Pearson)이 0.95를 넘는다. 못 채운 층은 N/A다.
  - 조건 정밀도: 「충족」 판정만, 규칙이 자동으로 막은 칸은 뺀다.
  - LV 정밀도: 확정된 LV는 전부 적고 「n개 중 m개 + 신뢰구간 + 확정 비율」로만 보고한다. 지금 확정될 수 있는 판정은 9~20개라, 9개가 모두 맞아도 하한이 약 70%다. LV에 대해서는 「95%」라고 주장하지 않는다. 사람은 확정했는데 시스템은 미확인인 놓침도 함께 잰다.
- 평가자: 같은 레포를 함께 한 동의자가 두 번째 평가자를 맡는다(Capstone1-Career는 ldm310·lsy341·Seonye32, veritas는 sangwon5579·sweetholly). 개발자는 남의 LV를 적지 않는다. ldm310은 결과를 이미 봤으므로 따로 보고한다. 20% 이상을 이중으로 적어 일치도(가중 카파)를 합의 전에 낸다.
- 절차: 4번을 정한 뒤 SHA와 규칙 지문(rule_hash)을 고정하고 빈 표를 만든다. 적은 시각을 기록하고, 정답 파일은 비교 전에 commit한다. 1인당 시간은 아직 잰 적이 없어(빈 표가 대상마다 33줄) 한 명으로 먼저 잰다.
- 동의: 지인 9명에게 동의 범위(분석, 라벨, 발표 노출, 보관)를 서면으로 받는다. 결과는 이 10명(편의 표본)에 한정된다고 밝힌다.
- 확정 표본 늘리기: 지인이 자기 레포에 ④를 넣으면 확정 가능한 판정이 늘어난다.

### 6. 서비스 연결 — FastAPI 분석 작업자 + 진행 조회(보완)
- 추천: Python 코드를 FastAPI로 감싼다. 작업 상태는 DB 표에 저장해 재시작해도 남게 하고, 별도 작업자 프로세스가 한 번에 1~2계정만 처리한다. Next.js는 2~3초마다 진행 상황을 받아 보여 준다.
- 꼭 넣을 것:
  - URL을 받으면 동의 기록부터 확인한다(CLI와 같은 관문). 나중에는 GitHub 로그인으로 본인을 확인한다.
  - 분석 서버는 127.0.0.1에만 열고 Next.js 서버가 대신 부른다.
  - 레포 목록은 API로 바로 보여 준다. 레포별 clone·blame은 4개 안팎으로 병렬로 돌려 끝나는 대로 채운다(첫 화면 R9).
  - GitHub API는 적은 동시성으로 부르고, 한도 초과와 5xx는 재시도한다.
  - SQLite는 WAL과 busy_timeout을 켜고, 같은 레포 캐시에는 잠금을 둔다.
  - 단계별로 시간 상한을 두고, 예산은 DB 장부로 함께 쓴다.
- 이유(정정): FastAPI를 쓰는 이유는 세 가지다. Spring BE와 Next.js가 함께 부를 수 있는 경계가 생기고, 시험을 통과한 Python 코드를 그대로 쓰고, 분석기를 읽기 전용 작업자로 떼어 둘 수 있다. Next.js가 Python을 따로 띄우고 작업 ID로 조회해도 시간 초과는 없다. 그 방식의 약점은 프로세스 관리와 팀 BE와의 경계다. 측정상 지금 수집만 41~283초라 R8·R9는 병렬화 뒤 다시 재야 한다.
- 결정(팀): Python 분석 서버를 팀 구조에 넣을지, 저장 DB(SQLite에서 PostgreSQL로 옮길 때). PostgreSQL 스키마는 문법만 확인했고 실제로 만들어 본 적은 없다. 그림 9도 고쳐야 한다.

  - 재지 않은 값은 N/A로 둔다.
- 역할: 요구와 정책은 학생이 날짜와 함께 정했다(R1~R10, B안 취소). AI가 코드를 쓰고, 기계 시험과 사람 정답 세트가 검증한다.
- 강도: 무거운 절차(작업마다 새 에이전트 + 2단계 검토)는 틀리면 거짓 인정이 나는 귀속·규칙에만 쓰고, 화면 연결은 가볍게 진행한다.

- squash·복사 되찾기 방법(6장)
