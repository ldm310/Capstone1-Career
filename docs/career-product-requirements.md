# Career 통합 요구사항 문서

> 2026-10-03 업데이트: 공고 카드 비교 표시·지원 직접 확인·수준별 스터디·High 포함 로드맵·필터 정책은 [공고별 스터디 FE 결정 및 구현 범위](./job-study-frontend-2026-10-03.md)를 우선한다. 아래 ‘문서 저장만’ 범위는 2026-09-30 당시 작업 기록이며, 10월 3일에는 해당 범위의 FE 개발이 별도 요청되었다. 기술별 LV 및 상대 수준 산정 기준은 계속 미정이다.

- 기준일: 2026-09-30
- 문서 목적: 대화와 사용자 첨부 문서의 요구사항을 통합하고, 미정 사항을 결정하지 않은 상태로 보존한다.
- 이번 작업 범위: 문서 저장·정리만 수행한다. 서비스 코드, UI, 데이터베이스, 배포, 커밋·푸시는 변경하지 않는다.
- 구현 상태: 이 문서는 개발 목표와 정책을 기록한다. 기능이 이미 구현됐거나 분석 성능이 검증됐다는 뜻이 아니다.
- 적용 순서: 사용자의 최신 명시적 결정이 과거 요청과 어시스턴트 제안보다 우선한다. 이후 별도 결정이 생기면 해당 항목을 갱신한다.
- 통합 기준: 채용공고 메뉴·조건 비교의 기존 결정 기록은 `recruitment-requirements-2026-09-30.md`에 보존하며, 통합 범위는 본 문서를 기준으로 확인한다.

## 1. 상태 정의

| 상태 | 의미 |
| --- | --- |
| 확정 | 사용자가 명시적으로 요청하거나 결정한 사항 |
| 개발 목표 | 사용자가 통합을 요청한 최신 기능표의 기능 범위. 세부 운영 정책의 확정까지 의미하지 않음 |
| 미정 | 사용자가 결정하지 않은 사항. 제안·권장안은 확정값으로 사용하지 않음 |
| 제외 | 최신 요구에서 개발하지 않기로 정한 사항 |

‘추천 기능’, ‘권장안’, ‘경쟁력이 높다’는 이전 설명을 확정 정책이나 검증된 효과로 취급하지 않는다.

## 2. 서비스 목적과 기본 흐름

서비스명은 **Career**이다. 한국어 사용자가 처음 방문해도 자신의 경험을 확인하고, 공고의 조건과 비교하며, 지원 검토 또는 추가 준비로 이동할 수 있어야 한다.

핵심 흐름:

**내 경험 확인 → 공고와 비교 → 지원 검토 또는 추가 준비 → 결과 확인·활용**

사용자가 얻을 결과:

1. 현재 자료에서 어떤 경험과 기술의 근거를 찾았는지 알 수 있다.
2. 목표 공고의 자격요건·우대사항 중 어떤 항목과 연결되는지 확인할 수 있다.
3. 기존 자료를 더 설명하면 되는 부분과 새 작업을 준비할 부분을 구분할 수 있다.
4. 기존 프로젝트에서 무엇을 어떤 순서로 보완할지 확인할 수 있다.
5. 작업 결과에서 확인된 내용과 남은 부분을 확인하고 지원 자료로 활용할 수 있다.

자료에서 찾지 못한 경험을 곧바로 사용자의 능력 부족으로 단정하지 않는다. 기능 목록만으로 경쟁 서비스 대체, 합격률 향상, 재사용 의향이 입증됐다고 주장하지 않는다.

초기 타겟을 AI·AX·LLM 신입·주니어로 제한하는 안은 제안 상태이다. **직무·경력 범위는 미정(U01)**이다.

## 4. 자료 등록과 첫 이용 경험

### 확정된 방향

- 주 입력 수단은 **GitHub 링크 / PDF / Markdown 파일**이다. 과거 GitHub·Notion·이력서·자격증을 각각 연결하던 구성을 이 방향으로 변경한다.
- 이력서·자격증 관련 정보는 PDF 등과 사용자 확인으로 보완할 수 있다. 별도 Notion 연동을 필수로 요구하지 않는다.
- 모든 자료를 한꺼번에 요구하지 않고 자료 하나로 시작한 뒤 추가할 수 있게 한다.
- Markdown은 ‘학습 노트·프로젝트 설명 파일(.md)’처럼 설명한다.
- 첫 이용 흐름은 **목표 직무 선택 → 자료 추가 → 결과 확인·수정 → 필요한 준비 시작**으로 안내한다.
- ‘정규화’, ‘수준 추출’, ‘Agent 검증’ 같은 처리 용어보다 사용자가 얻는 결과를 먼저 설명한다.
- 기술 이름의 여러 표기는 공통 기술명으로 정리하되, 잘못 연결된 기술은 수정할 수 있어야 한다.
- 원문 근거와 기술 이름·결과의 연결을 보존한다.

### 미정 연결

- 프로젝트가 없는 사용자에게 제공할 별도 경로: U02.
- 공개·비공개 저장소 접근 범위: U04.
- 사용자 수정이 인정 상태에 미치는 영향: U05.
- 파일 크기·페이지 수·저장소 크기·스캔 PDF 지원 등 처리 범위: U16.

## 5. LV와 분석 결과의 의미

### 확정된 방향

- **사용자 기술의 LV**는 제출 자료에서 기술별 기준에 따라 확인된 단계를 표시하기 위한 것이다. 실제 지식·실력 전체를 확정하는 등급으로 표현하지 않는다.
- **과제의 LV**는 과제 범위와 완료 기준에 따른 단계이다.
- **공고에는 LV를 부여하지 않는다.** 공고가 요구하는 경험·행동과 사용자 자료를 비교하며, 관련 기술의 사용자 LV는 함께 볼 수 있다.
- 공통 명칭은 LV1 ‘기초 사용’, LV2 ‘프로젝트 적용’, LV3 ‘개선·문제 해결’이다.
- 현재 확인 단계, 다음 과제 단계, 보상을 구분해서 보여준다.
- 기존 자료로 인정한 단계는 ‘기존 역량’으로 표시한다. ‘완료했는데 0점’으로 보이지 않도록 보상 규칙을 설명한다.
- 자료가 부족하면 판단을 보류하고, 어떤 자료를 추가하면 되는지 안내한다.
- 코드 파일이 있다는 사실, 실행 결과가 있다는 사실, 사용자가 직접 수행했다는 사실을 동일하게 취급하지 않는다.
- PDF에 적힌 자기 서술과 코드·실행으로 확인한 내용을 구분한다.

### 아직 확정되지 않은 기준

기술별 LV 완료 기준·필수 증거·평가 범위는 **U06**, LV 간 선행·포함 관계는 **U07**이다. 과거 대화의 Dockerfile·Compose·RAG 예시는 승인된 기준표가 아니다. 파일 하나로 자동 인정하거나 특정 도구를 모든 사용자의 필수 기준으로 확정하지 않는다.

## 7. 자격요건을 먼저 확인하는 공고 비교

### 확정된 순서 및 표시 원칙

1. 공고의 자격요건을 먼저 추출하고 사용자 자료·정보와 비교한다.
2. 자격요건 결과를 먼저 보여준다.
3. 우대사항을 별도로 분석하고 그 결과를 다음에 보여준다.
4. 공고 원문과 사용자 근거를 연결하고 추가 확인할 내용을 안내한다.

자격요건과 우대사항 결과는 분리한다. 우대사항이 여러 개 연결돼도 필수 조건 불일치를 상쇄하지 않는다. 우대사항이 없다는 이유만으로 자격요건 미달로 처리하지 않는다
**자격요건을 먼저 파악하고 비교한 다음, 우대사항을 별도로 파악하고 비교한다.** 결과도 자격요건을 먼저, 우대사항을 그다음에 보여준다.

### 조건별 비교 상태

| 상태 | 의미 |
| --- | --- |
| 관련 근거 확인 | 해당 조건과 연결되는 자료를 찾음 |
| 일부 확인 | 해당 조건의 일부 내용만 확인 가능 |
| 추가 확인 필요 | 현재 자료만으로 판단할 수 없음 |
| 명시 조건과 불일치 | 명확한 공고 조건과 확인된 사용자 정보가 다름 |

‘관련 근거 확인’은 기업이 자격 충족을 최종 인정했다는 뜻이 아니다. 자료를 찾지 못한 사실만으로 ‘충족 불가’ 또는 ‘지원 불가’로 단정하지 않는다.

### 반드시 구분할 경우

| 자격요건 | 우대사항 | 표시 방향 |
| --- | --- | --- |
| 명시 조건과 불일치 | 2~3개 관련 근거 확인 | 자격요건의 차이를 먼저 알리고 우대 경험 별도 표시 |
| 관련 근거 확인 | 근거 없음 | 자격요건 결과는 유지하고 우대사항은 미확인으로 표시 |
| 추가 확인 필요 | 여러 개 관련 근거 확인 | 자격요건의 추가 확인을 우선 안내 |
| 관련 근거 확인 | 일부 또는 전체 관련 근거 확인 | 두 결과를 각각 표시. 합격 확률로 변환하지 않음 |

- 필수·우대·담당 업무를 혼동하지 않는다.
- ‘A 또는 B’ 조건을 둘 다 필수인 것으로 바꾸지 않는다.
- 명시되지 않은 도구·기술·경력 조건을 임의로 추가하지 않는다.
- 개인 프로젝트 과제로 상용 경력·협업 경력을 자동 충족 처리하지 않는다.
- 우대사항 개수만으로 ‘합격 가능성이 높다’고 표시하지 않는다.

### 마감 안내와 지원 동선

- 마감일·시각이 제공된 범위에서 표시하고, 없는 시각을 임의로 생성하지 않는다.
- 공고 최종 확인 시점을 보여준다. 갱신·마감 처리 주기는 U17 미정이다.
- 오늘 할 수 있는 자료 확인·기존 경험 정리와 장기 보완 작업을 구분한다.
- **개발 목표상의 안내 원칙:** Career의 특정 LV 또는 과제 완료를 공고 열람·지원 동선의 필수 조건으로 삼지 않는다. 사용자가 질문한 해당 문구에는 이 의미를 설명했으며, 별도의 잠금 정책은 결정하지 않았다.
- 위 원칙은 기업의 필수 조건을 무시해도 된다는 뜻이 아니다. 실제 지원 접수는 채용처 기준을 따른다. Career 내부 직접 지원 기능은 확정되지 않았다.

## 8. 맞춤 과제와 학습 경로

- 학습·구현 순서 기능은 유지한다. 경쟁 서비스에도 있다는 이유로 제거하지 않는다.
- 기술명 목록만 제시하지 않고 무엇을 만들고 확인할지 설명한다.
- 공고 조건, 현재 프로젝트, 이미 확인한 경험, 선행 작업, 선택한 목표와 시간을 연결한다.
- ‘지금 할 작업 / 다음 작업 / 함께 할 작업 / 선택 작업’을 구분한다.
- 기존 프로젝트에 필요한 수정 작업과 단순한 설명·근거 보완을 구분한다.
- 여러 공고에서 공통으로 활용할 수 있는 작업을 묶되, 합격률로 환산하지 않는다.
- 과제에는 추천 이유·완료 기준·제출할 근거·단계·보상이 필요하다.
- Python → RAG·Vector DB → LangGraph → Docker·MCP 같은 과거 경로는 예시이다. 모든 사용자에게 필요한 고정 순서로 확정하지 않는다.
- 과제 생성 방식·기준 변경 정책은 U09, 검토 방식은 U10이다.

### 이전 UI 요청 중 유지할 사항

- 학습 경로는 순서를 숫자로 표현한다.
- 순서 선택 시 하단 항목을 위로 재배치하지 않고, 해당 위치에서 관련 세부 내용을 확인할 수 있게 한다.
- 학습 경로 아래의 **전체 과제 목록을 유지**한다.
- 이 배치를 새 정보 구조에 적용하는 상세 화면 설계는 U13과 함께 정리한다.

## 9. 결과 확인·재분석·지원용 활용

- 제출 결과는 완료 기준별로 무엇을 확인했고 무엇이 남았는지 보여준다.
- ‘확인 중’, ‘추가 자료 필요’, ‘완료 확인’, ‘재검토 요청’에 해당하는 사용자 상황을 설명한다. 실제 상태 전이·처리 주체는 U10에서 확정한다.
- 실행·테스트·평가 결과를 확인 가능한 범위에서 제시한다. 자동 검증을 모든 과제에 제공한다고 확정하지 않는다.
- 현재 분석 결과, 당시 과제 완료 기록, 포인트 내역을 구분해 보존한다.
- 재분석 전후 새로 확인된 근거와 여전히 미확인인 부분을 비교한다.
- 지원용 자료는 공고에 관련된 프로젝트·담당 역할·작업 결과·원문 링크를 모아 활용할 수 있어야 한다.
- 출력 형식, 공개 공유 범위, 출력 문장 자동 작성 여부는 U12-E에서 결정한다.
- **일반 이력서 작성 서비스·AI 면접 기능은 개발 제외**이다. 근거 정리·내보내기를 이력서 전체 자동 생성이나 면접 코칭으로 확대하지 않는다.

## 10. 성장 대시보드·포인트·랭킹

### 확정 정책

- 성장 대시보드는 완료 과제, 새로 확인된 근거, 남은 준비, 포인트를 보여주는 보조 기능이다.
- 최초·기존 자료로 인정받은 역량 자체에는 포인트를 지급하지 않는다.
- 기존 자료로 역량을 파악한 후 부족한 부분을 보완한 활동에 보상한다.
- 보완 과제 완료 확인 시 **LV1 10점 / LV2 20점 / LV3 30점**을 적용한다.
- 중복 제출·재시도에 중복 지급되지 않아야 한다.
- 랭킹은 실력·취업 경쟁력 순위가 아닌 **성장 포인트 랭킹**으로 표현한다.
- 비공개 사용자는 목록과 순위 계산 모두에서 제외한다.
- 동점 순위는 **1·1·2위** 방식이다.
- 랭킹 참여 여부와 관계없이 개인 포인트는 확인할 수 있다.
- 체험 데이터는 실제 순위에서 제외한다.

### 미정 정책

- 한 과제로 복수 단계 충족 시 합산 여부, 같은 단계 반복 보상, 재분석·오지급 정정과 회수는 U11.
- ‘같은 기술·같은 단계 보상은 1회’와 ‘시작 과제 보상만 지급’은 이전 권장안일 뿐 확정하지 않았다.
- 랭킹 집계 기간·참여 기본값·실제 게스트 기록의 랭킹 참여·계정 전환 시 처리·표시 이름은 U15.

## 11. 공통 UI/UX 및 기존 디자인 방향

- 서비스명은 Career, 주요 메뉴·안내·오류 메시지는 한국어로 제공한다.
- 개발자가 아닌 첫 사용자 관점에서 기능의 목적과 다음 행동을 설명한다.
- 홈페이지에서 주요 기능으로 바로 이동할 수 있도록 한다. 각 기능 안에서는 그 영역에 속한 메뉴를 중심으로 구성한다.
- 기존 상위 기능 영역은 채용공고·내 역량 확인·취업 준비·지원 관리·성장 대시보드이다. ‘지원한 공고’가 채용공고 안에 포함된 뒤 상위 ‘지원 관리’를 유지할지 통합할지는 U13 미정이다.
- 공고가 실제 연동 자료인지 예시인지, 분석이 실제 결과인지 체험인지 구분한다.
- 오류·미확인·추가 자료 요청은 이유와 다음 행동을 함께 안내한다.
- 글꼴·자간·화살표 정렬을 일관되게 유지한다.
- 기존 요청의 하늘·밝은 구름 디자인을 유지한다. 인트로와 홈페이지에 같은 구름 이미지 구성을 적용하고, 5초 간격 이미지 전환을 요청한 상태다.
- 인트로는 큰 Career 제목·부제목과 ‘나의 Career 만나보기’ 텍스트·오른쪽 화살표·밑줄 형태의 시작 버튼 방향을 유지한다.
- 장식보다 기능 목적이 잘 읽히는 아이콘과 문구를 사용한다. 단계 순서는 아이콘 대신 숫자를 사용한다.
- 로그인 없이 서비스 흐름을 확인할 수 있게 해 달라는 이전 요청은 유지한다. 최종 계정·저장·운영 범위는 U14 미정이다.
- 실제 사용자에게 자료 등록부터 공고 비교·과제 결과 확인까지 수행하게 해 이해도와 편의성을 검증할 필요가 있다. 아직 효과가 입증됐다는 의미는 아니다.

## 13. 기술 제안과 효과 검증의 상태

- 과거 언급한 Next.js·TypeScript, Gemini, Zod, PostgreSQL, BullMQ·Redis, GitHub API, Tree-sitter, 격리 실행 도구는 구현 검토안이다. 기존 코드에서 이미 쓰는 기술이 있더라도 전체 운영 기술 선택이 확정됐다고 간주하지 않는다.
- ‘Agent를 반드시 사용한다’는 결정은 없다.
- 특정 모델이 다른 모델보다 우수하거나 검증 정확도가 확보됐다는 실측 결과는 본 문서에서 주장하지 않는다.
- 기술 선정은 정확도, 원문 근거 추적, 처리 시간·비용, 재시도, 보안·실행 격리, 기존 프로젝트와의 통합 비용을 비교해 결정할 대상이다.
- 사용자 가치 검증 후보: 보완 작업 결정 시간, 잘못 추천한 작업 비율, 실제 작업·지원 자료 반영, 자발적 재사용. 측정 계획·성공 기준은 U18 미정이다.

## 14. 문서 해석 및 후속 변경

- 개발 목표 기능은 사라지지 않도록 보존하되, 미정 정책에 임의의 기본값을 넣어 확정하지 않는다.
- 이후 개발 요청 시 관련 미정 항목을 확인하고 구현 범위를 구분한다.
- ‘설명한 기능’과 ‘검증된 경쟁 우위’, ‘자료 확인’과 ‘실력 보증’, ‘지원 검토 안내’와 ‘기업 자격 인정’을 구분한다.
- 이번 문서 작성으로 코드 개발·배포·외부 서비스 쓰기 작업을 시작하지 않는다.
