# Career LV 판정 구성 및 LangGraph 도입 벤치마크

작성일: 2026-10-02. 이 문서는 **최종 비교 설계와 현재까지의 실측 결과를 통합한 문서**다. 최종 평가 완료 보고서는 아니다. 현재 판정 구성 우승자와 LangGraph 도입 여부는 **결정 보류**다.

## 1. 결정할 두 가지

1. 어떤 판정 구성이 제출 자료의 기술 활용 수준을 가장 적절하게 평가하는가?
2. 같은 평가 절차를 운영할 때 일반 Python보다 LangGraph StateGraph를 도입할 실익이 있는가?

LangGraph는 여섯 번째 판정 방식이 아니다. StateGraph는 LangGraph의 실행 구성이다. 판정 품질 비교와 실행기 비교는 별도 실험으로 진행한다.

## 2. 사용자 확정 LV 기준

| 단계 | 핵심 기준 | 필요한 증거 |
|---|---|---|
| LV1 · 기초 사용 | 해당 기술로 기본 기능을 구현하고 실행할 수 있음 | 구현 코드, 재현 가능한 실행 방법·결과 |
| LV2 · 프로젝트 적용 | 프로젝트 요구사항에 맞춰 다른 기능과 연결하고 동작을 검증함 | 연동 코드, 요구사항에 대응하는 테스트, 적용 이유 |
| LV3 · 개선·문제 해결 | 문제를 측정·분석하고 수정한 뒤 효과와 한계를 설명함 | 문제 분석, 변경 코드, 동일 조건의 전후 평가, 결과 해석 |

현재 기술 범위는 RAG다. 상위 LV는 하위 LV를 포함한다. 근거 부족은 unknown, 상충 근거는 conflict, 확인 가능한 LV가 없으면 null이다. null을 LV1이나 능력 0으로 해석하지 않는다. 개인 기여는 기술 수준과 별도로 확인한다.

구현 기준표: [rag.confirmed-v2.json](../config/rag.confirmed-v2.json). 위 단계 정의는 사용자가 확정했으며, 세부 근거 해석과 추출 규칙의 타당성이 검증되었다는 의미는 아니다.

## 3. 판정 구성 비교

| 구성 | 원문 접근 및 분석 | 최종 LV 결정 | 주로 확인할 점 |
|---|---|---|---|
| A. Rule-only | 코드·문서·설정·실행 기록을 규칙으로 분석 | 공통 판정기 | 규칙 범위 밖 표현, 미확인 처리, 실행 속도 |
| B. LLM-only | 전체 원문과 공통 기준을 모델에 제공 | 모델 직접 판정 유지 | 과대 인정, 인용 오류, 반복 일관성 |
| C. 고정 워크플로 | 자료 준비 → LLM 해석 → 근거 검사 → 판정 | 공통 판정기 | 해석 품질, 검증 단계 효과 |
| D. Single-agent | 하나의 Agent가 읽기·검색·종료를 선택 | 공통 판정기 | 탐색 누락과 자원 사용 |
| E. Multi-agent | 분석자와 검토자가 각각 원문 탐색 | 공통 판정기 | 검토의 실익, 추가 자원, 누적 오류 |

A/C/D/E는 같은 판정기를 사용한다. 인용의 원문 존재 여부와 기준을 뒷받침하는 충분성은 별개다. 검토자의 동의만으로 정답을 만들지 않는다.

## 4. 현재 실제 모델 실행 결과

자료: `ruizguille/rag-from-scratch`, 커밋 `0f2f4927873fde7d8479c243a21a77ea8a391e9a`. 공개 프로젝트 1개, 구성별 1회. 코드와 문서를 읽었으며 제출 프로그램은 실행하지 않았다. Gemini `gemini-3.5-flash-lite`, temperature=0.

|---|---|---|---:|---:|---:|---:|---:|

| B | 완료 | null·추가 확인 | 4.316 | 1 | 8 | 3992 | 1150 |
| C | 완료 | null·추가 확인 | 3.961 | 1 | 8 | 3985 | 1174 |
| D | 완료 | null·추가 확인 | 14.744 | 8 | 6 | 11684 | 2538 |
| E | HTTP 429 중단 | 결과 없음 | 11.353·중단 시점 | 7 | 4 | 10648 | 2313 |

- 실행 시간은 평균이나 p95가 아닌 단일 관측값이다. E의 시간은 완료 지연이 아니다.
- 모델 요청 수에는 실패 요청을 포함한다. 토큰은 응답으로 확인된 값만 합산했으며 실패 요청 토큰은 미확인이다.
- 자료 도구 호출에는 비에이전트의 일괄 자료 로딩도 포함된다. 횟수만으로 탐색 효율을 단정하지 않는다.
- A는 신규 세부 기준 일부가 미구현 상태인 기준선이다. Rule-based 전체를 대표하지 않는다.
- 실행 결과 자료가 없어 모든 완료 구성이 보류했다. 기준별 상태에는 차이가 있었다. 사람 검토 답안이 없어 어느 해석이 정확한지는 확정하지 않는다.
- E의 한도 오류에는 선행 구성의 누적 API 사용이 영향을 줄 수 있다. Multi-agent 자체의 신뢰성 열위라고 단정하지 않는다.
- 실제 비용·정확도·과대/과소 인정·근거 오류·반복 일관성은 N/A다. 무료 등급 가능성과 실제 청구액 확인은 별개다.

상세: [첫 live 보고서](confirmed-v2-live.md). 원시 결과는 `artifacts/runs/confirmed-v2-live/`에 Git 제외 상태로 보관한다. 초기 2.5 Flash-Lite 요청의 404 실패는 해당 보고서에 따로 기록했다.

| 항목 | 적용할 조건 | 현재 상태 |

외부 API 할당량을 프로그램이 늘릴 수는 없다. 계정의 실제 한도에 맞춰 호출 간격과 배치를 정한다. 재시도는 횟수·대기·실패 사용량을 포함해 기록한다. 모델 대기 시간과 할당량 대기 시간을 별도 열로 남긴다.

## 6. 데이터와 기준 답안

첫 5~10개 서로 다른 프로젝트로 파일럿을 시작하고 이후 30~50개로 확대한다. LV1/LV2/LV3, 언급·의존성만 존재, 실행 결과 없는 테스트, 자료 부족, 상충 자료를 포함한다. 실제 자료가 특정 수준의 조건을 충족하지 않으면 억지로 그 수준에 배정하지 않는다.

개발/최종 평가는 project_id로 분리한다. 동일 프로젝트 변형은 같은 분할에 둔다. 최종 자료는 규칙·프롬프트 조정에 사용하지 않는다. 합성 자료는 회귀 테스트로만 별도 관리한다.

AI가 파일·줄 인용과 답안 초안을 작성하고 사람이 원문을 검토한다. 초기 한 명으로 시작할 수 있지만 최종 보고용은 두 검토자의 독립 판정과 불일치 조정을 권장한다. 최종 LV, 기준 상태, 인용 존재 여부, 충분성, 실행/기여 구분을 기록한다. gold는 모델과 도구 허용 경로 밖에 둔다.

## 7. 지표와 분모

| 지표 | 계산 단위·분모 | 실패·미검토 처리 |
|---|---|---|
| 최종 LV 일치율 | 검토 답안이 있는 고유 사례 중 첫 사전 지정 실행의 완료 판정과 정답이 같은 수 / 비교 가능한 완료 사례 수 | 완료율도 함께 표시; 시스템 오류를 정답 null로 계산하지 않음 |
| 기준별 일치율 | 같은 조건에서 상태가 맞은 기준 수 / 비교한 기준 수 | 누락 기준 처리 정책 사전 고정 |
| 과대/과소 인정 | 비교 가능한 고유 사례별 과대/과소 건수 및 비율 | null 대 유효 LV는 별도 표기; null은 능력 0이 아님 |
| 근거 오류 | 사람이 오류로 확인한 인용 수 / 사람이 검토한 인용 수 | 원문 부재와 의미 불충분 분리, 검토 없으면 N/A |
| 판정 범위 | 유효 LV가 나온 고유 사례 수 / 전체 고유 사례 수 | 완료 사례만 분모인 조건부 범위도 별도 표시 |
| 보류·불필요한 보류 | 정상 완료의 null 보류 수; 그중 정답 LV가 있는 수 | 시스템 오류 별도, 정답 없으면 불필요한 보류 N/A |
| 반복 일관성 | 반복 모두 상태·LV·기준 판정이 같은 사례-구성 그룹 수 / 반복 그룹 수 | 반복을 표본 수에 더하지 않음 |
| 실패율 | 실패 실행 수 / 전체 실행 수 | API 한도·네트워크·스키마·예산 초과 분리 |
| 처리 시간 | 완료 실행의 평균·중앙값·p95, 실패 경과 시간 별도 | 작은 표본 p95 불안정성 명시 |
| 호출·토큰·비용 | 성공·실패·재시도를 합산한 사례별 사용량 | 알 수 없는 실패 토큰/단가/비용은 N/A |

위 표는 최종 집계 사양이다. 기존 집계기의 모든 항목이 이 정의를 구현했다고 간주하면 안 된다. 특히 현재 일반 집계는 첫 실행 기반이고, 실패 사용량 및 미검토 근거 오류 처리를 보완해야 한다.

## 8. 사전 선택 조건

기존 파일럿 결과를 이미 보았으므로 아래 조건은 **앞으로 별도로 확보할 최종 평가 자료의 결과를 보기 전에** 확정한다. 아래 값은 모두 팀 입력 사항이며 임의의 합격 수치를 부여하지 않았다.

| 조건 | 확정값 | 역할 |
|---|---|---|
| 최소 최종 LV·기준별 일치율 | 미정 | 품질 하한 |
| 최대 과대 인정률·근거 오류율 | 미정 | 잘못된 인정 제한 |
| 최소 판정 범위·최대 불필요한 보류율 | 미정 | 모든 사례 보류로 통과하는 것 방지 |
| 최대 실패율 | 미정 | 실행 안정성 |
| 최대 p95 시간·사례당 비용 | 미정 | 운영 가능성 |
| 최소 의미 있는 차이·동률 처리 | 미정 | 작은 표본의 우연한 차이로 승자 선정 방지 |

모든 필수 품질 조건을 통과한 후보들 중 비용·시간·유지보수 부담을 비교한다. 비용과 시간의 우선순위도 사전에 정한다. 서로 다른 장점이 있으면 후보를 유지한다. 어떤 후보도 통과하지 못하면 승자 없음이다. 표본 수와 불확실성을 함께 보고한다.

## 9. LangGraph 실행기 비교

C의 같은 prepare/interpret/verify/decide 논리를 일반 Python과 LangGraph StateGraph로 실행한다. 모델·프롬프트·기준·원본을 유지하고 실행기만 바꾼다. 저장된 동일 모델 응답으로 replay하며, 필요한 도구 응답도 고정한다. 둘 다 외부 DB 서버 없이 SQLite 지속 체크포인트를 사용한다.

| 각 단계 저장 전/후 실패 | 같은 경계에 실패 주입 | 보존 상태, 재계산 단계, 실제 모델/도구 요청 건수 |
| 프로세스 종료·재시작 | 새 프로세스·동일 thread ID·지속 저장소 | 복구 성공 건수/시도 수, 복구 시간 |
| 요청 후 저장 전 중단 | 외부 호출과 checkpoint 사이 동일 실패 위치 | 중복 요청·중복 결과, 비용 미확인 구간 |
| 구현 부담 | 저장·복구·중복 방지·로그 기능 범위 동일 | 직접 작성 코드·의존성·수정 작업량 및 한계 |

일부 지원이 없으면 미지원으로 표시한다. checkpoint만으로 외부 호출의 정확히 한 번 실행을 보장한다고 가정하지 않는다. v2 자료에서도 다시 확인해야 한다.

### 도입 결정 조건

- **도입 후보:** 서비스에 상태 보존·복구·분기 관리가 필요하고, 동일 기능을 맞춘 비교에서 LangGraph가 유지보수 부담을 줄이며 사전 지연·비용 조건을 충족한다.
- **일반 Python 유지 후보:** 필요한 흐름이 단순하고 현재 저장·복구 기능으로 요구사항을 충족하며 LangGraph의 추가 실익이 확인되지 않는다.
- **현재 결론:** 두 실행기 모두 제한된 기존 복구 시나리오는 통과했으나, 측정 경계·호출 계수·v2 검증을 보완하기 전 도입 결론을 내리지 않는다.

이 결론은 해당 고정 워크플로에만 적용한다. D/E의 복잡한 Agent 구조로 일반화하려면 별도 실험이 필요하다.

## 10. 최종 실행·보고 순서

1. v2 Rule-only 지원, 인용 검사, 예산 선차단, 실패 사용량 보존, 전체 실행기의 v2 선택을 보완하고 테스트한다.
2. 5~10개 프로젝트를 수집하고 검토 답안과 프로젝트 단위 분할을 만든다.
3. 새로운 최종 자료를 보기 전에 선택 조건을 기록한다.
4. 할당량에 맞춰 순서를 교대하고 구성별 3회 live 실행한다. 같은 자원 조건의 추가 비교를 분리한다.
5. 동일 응답 replay로 Python/StateGraph의 정상·실패·복구 실험을 진행한다.
6. 품질 통과 여부와 비용·시간을 먼저 판정하고 LangGraph 도입 결론은 별도 표로 제시한다.

현재 재실행 가능 명령(완성된 최종 평가 자동화가 아님):

```bash
cd experiments/lv-evaluation
.venv/bin/pytest
# v2 공개 프로젝트 1개 live; 기존 같은 경로의 보고서를 갱신함
.venv/bin/python -m lv_eval.pilot
# v1 저장 응답 실행기 확인; 최종 오버헤드 실험은 아님
.venv/bin/lv-eval compare-runners --case-id project_lv2 \
  --replay-file data/replay/project_lv2.workflow.jsonl \
  --checkpoint-dir artifacts/checkpoints \
  --output artifacts/runs/runner-check
```

## 11. 현재 결정 상태
