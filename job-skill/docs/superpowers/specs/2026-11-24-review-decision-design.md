# 사람 검토(정상·제외·다시)를 추출 실행 표에 — 설계

2026-11-24 · 사용자 결정으로 정함

## 왜

- 추출 결과에 '검토 사유'가 붙은 공고는 사람이 본다. 보는 사람은 사용자(역량 추출 담당)이고, 화면은 팀원(백엔드)이 만든 관리자 페이지다.
- 팀원은 별도 표(`career_extraction_review`)와 DAG 쪽 파이썬 코드(`extraction_review.py`)로 만들었다. 그런데 다음 문제가 있다.
  - 재추출하면 공고의 직무·경력 조건이 지워진다.
  - '검토 필요' 결과를 실패로 세어, 2번 쌓이면 자동 재추출이 막힌다.
  - DAG 영역(사용자 담당) 코드를 팀원이 고쳤다.
- 사용자 결정: 별도 표 대신 **사용자 표(`extraction_run`)에 칸을 더해서** 하고, DAG 쪽은 사용자가 직접 맡는다.

## 목표

- 관리자 페이지에서 고르는 단어는 셋이다.

  | 단어 | 뜻 | 그 뒤 |
  |---|---|---|
  | 정상 | 결과가 맞음 | 검토 목록에서 빠진다. 공고가 수정되면 평소처럼 다시 추출한다. |
  | 제외 | 이 공고는 다루지 않음 | 수정돼도 다시 추출하지 않는다. 변경·마감 확인도 하지 않는다. 웹에도 보이지 않는다. |
  | 다시 | 피드백을 적어 재추출 | 다음 ① 매일 수집 때 피드백을 LLM 입력 끝에 붙여 다시 추출한다. |

- 다시 추출한 뒤에는 새 결과가 현재 결과가 된다. 옛 결과는 '다시'와 피드백을 단 채 남아, 피드백이 반영됐는지 비교할 수 있다.
- 새 결과에 또 검토 사유가 있으면 다시 검토 목록에 올라온다. 실패 횟수 같은 것은 세지 않는다.

## 하지 않는 것

- 웹 화면 고치기는 팀원 몫이다. 팀원에게 줄 안내 문서도 만들지 않는다(사용자 결정, 전달은 사용자가 한다).
- 바로 재추출하지 않는다. 다음 날 00:00 ①에서 처리한다.
- 누가 검토했는지는 기록하지 않는다. 검토하는 사람이 한 명뿐이다.

## 실패로 보는 것

- 팀원 계정이 검토 칸 말고 다른 칸을 쓸 수 있게 되는 것.
- 재추출 때 공고 정보(직무·경력·마감일)가 지워지거나 바뀌는 것.

## 방법 (고른 것: 3)

1. **팀원의 별도 표를 그대로 쓴다.** 관리자 페이지를 열 때마다 검토 목록을 별도 표에 복사(동기화)해야 하고, 두 표가 어긋날 수 있다. 사용자가 고르지 않음.
2. **보류 작업(2026-10-29)대로 '통과 여부(true/false) + 피드백'.** 제외를 나타낼 수 없다.
3. **비어 있는 `review_result` 칸을 정상·제외·다시로 바꾸고, 피드백 칸 하나를 더한다.** RDS 2,125건 모두 이 칸이 비어 있어 바꿔도 잃는 것이 없다. 사용자가 고름.

## DB (사용자가 정함 + 내 판단)

- 마이그레이션 `010_review_decision.sql`(내 판단). develop 에 팀원의 008·009 가 있어 번호가 겹치지 않게 010 을 쓴다. 여러 번 돌려도 같은 결과여야 한다.
- `extraction_run.review_result`: 받는 값을 `정상`, `제외`, `다시`로 바꾼다(지금 값은 모두 비어 있음).
- `extraction_run.review_feedback text`를 더한다. '다시'이면 꼭 채워야 한다(빈칸만이면 안 됨).
- 기존 제약 "검토 결과와 검토 시각은 둘 다 있거나 둘 다 없다"는 그대로 둔다.
- 검토 목록 색인 `extraction_run_review_queue`(검토 사유 있음 + 검토 결과 빔)도 그대로 둔다.
- 권한(사용자 결정): 지금 권한은 그대로 두고, 팀원 역할 `team`에 `extraction_run`의 `review_result`, `review_feedback`, `reviewed_at` 세 칸만 UPDATE 를 더한다.
- `schema.sql`, `docs`의 ERD 그림 2개(svg·png), `physical-design.md`도 같은 내용으로 고친다(사용자 요청).

## DAG

- **밀린 공고**(`db_queries.pending_postings`): 지금은 "추출 실행이 하나도 없는 진행 공고"다. 여기에 "현재 결과가 '다시'인 진행 공고"를 더한다.
  - 공고 정보(직무·경력·마감일)는 DB 에서 읽는다. 그래서 지워지지 않는다.
  - 피드백은 실행 폴더의 `feedback.json`에 따로 쓴다(내 판단, 줄바꿈이 있을 수 있어 targets.tsv 와 따로).
- **추출**(`extract_skills.py`): `feedback.json`에 있는 공고는 LLM 입력 끝에 `[검토 피드백]`과 그 글을 붙인다. 모집 단위 검사로 한 번 더 부를 때도 붙인다.
- **저장**(`db_load.insert_run`): 같은 입력이면 새 실행을 만들지 않는 규칙이 있다. 같은 피드백으로 두 번 '다시'를 하면 입력이 같아 막힌다. 그래서 '다시'인 실행은 이 비교에서 뺀다.
- **제외**: `open_postings`(수정·마감 확인 대상)에서 현재 결과가 '제외'인 공고를 뺀다. 아는 번호에는 그대로 들어 있어 새 공고로 다시 잡히지 않는다.
- **실패할 때**: 재추출이 실패하거나 비용 상한에 걸리면 현재 결과가 그대로 '다시'로 남아, 다음 날 또 밀린 공고로 잡힌다. 지금 밀린 공고와 같은 규칙이고, 실패는 지금처럼 Slack 결과 알림에 나온다.
- **마감된 공고**: 진행 공고만 밀린 공고가 된다. 마감된 공고에 '다시'를 눌러도 재추출하지 않는다(내 판단, 이미 끝난 공고라 비용을 쓸 이유가 없음).
- 결과 알림의 밀린 공고 수 옆에 그중 '다시'가 몇 건인지 적는다(내 판단).

## 팀원 작업 정리

- develop 의 팀원 파이썬 코드는 가져오지 않는다. 우리 브랜치를 develop 에 합칠 때 `extract_skills.py`, `pipeline_tasks.py`는 우리 것으로 두고 다음을 뺀다.
  - `extraction_review.py`, `configure_review_namespace.py`, `check_review_connection.py`
  - 그 시험 2개, `docs/teammate-airflow-connection.md`, `.env.example`의 `CAREER_PIPELINE_NAMESPACE`
- 팀원 표·뷰와 `008`·`009`·`sync_extraction_review.sql`은 웹이 아직 쓴다. 팀원이 웹을 새 칸으로 바꾼 뒤에 지운다. 표 주인이 팀원 계정이라 지우기도 팀원이 한다.
- 웹이 새 칸을 쓰는 법(검토 목록 = 현재 결과 + 검토 사유 있음 + 검토 결과 빔, '제외'는 숨김)은 `physical-design.md`의 칸 설명에 적힌 것으로 충분하다. 따로 안내 문서를 만들지 않는다.
