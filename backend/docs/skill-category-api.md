관련 묶음은 중복 가능하며 기술 분류를 확정하는 하위 카테고리가 아니다. 예를 들어 기타의 인프라 관련 42개에는 O와 기타가 함께 있는 복합 업무도 포함된다. ‘미배정’은 **기타 안에서 관련 묶음을 정하지 못함**을 뜻한다. 전체 카테고리 미분류 0과 구분한다.

자격증 101개는 기존 X 등에서 가져온 별도 참고 묶음이다. 이 101개를 기타 880개에 더하지 않는다. 관심·성실함·책임감처럼 구체 수행 근거가 없는 표현은 기타가 아니라 카운트 제외로 보존한다.

## 카테고리 조회 계약

### `GET /api/skill-categories`

버전 `flat-10-infra-review-20261119`, 기술 10개, 보조 태그, 기타 관련 묶음과 각 집계를 반환한다. `scope=SAVED_REVIEW_CORPUS_INCLUDING_HISTORY`, `categoriesOverlap=true`, `levelScoringEnabled=false`다. 기존 `GET /api/capabilities`의 평가용 capability ID와 별개다. 기존 사전·추출 JSON·LV 점수는 변경하지 않는다.

### `GET /api/postings/{postingId}/skill-categories`

현재 DB의 추출 문장을 저장된 검토 결과와 매칭한다. 모집 단위별로 `itemId`, `sourceCategory`, `text`, `assignment`를 반환한다. 원문 NFC·공백 정규화 후 SHA-256 완전 일치만 사용한다. 숫자·경력 조건이나 다른 단어를 임의로 지우거나 유사 문장으로 전파하지 않는다. 서버에는 벡터·원문 목록 없이 문장 해시와 분류만 묶어 배포한다.

| assignment.status | 의미 |
| --- | --- |
| CLASSIFIED | 저장된 분류 있음. `categoryCodes`에 기술·보조·OTHER 코드가 올 수 있음 |
| EXCLUDED | 카운트 제외. 코드 없음, `excludedFromCounts=true` |
| UNCLASSIFIED | 저장된 원문과 일치하지 않는 새 문장. 기타로 자동 처리하지 않음 |
| NOT_APPLICABLE | 필수·우대가 아닌 업무·기타 항목. 이번 분류 대상 밖 |

`needsReview`는 기존 모델 검토 플래그를 유지한다. 저장된 분류가 있다는 사실은 모든 문장이 사람 정답 검증을 통과했다는 뜻이 아니다. `relatedGroups`는 참고용 기타 묶음과 자격증이며 기술 축으로 집계하지 않는다. 아직 추출 전이면 `analysisStatus=NOT_ANALYZED`, 모집 단위는 빈 배열이다. 존재하지 않는 공고는 404다. API 조회 중 모델 호출·자동 LV 산정·DB 쓰기는 없다.

## 프론트 연결

브라우저 → Next.js `/api/jobs` → 서버 환경변수 `BACKEND_URL` → Spring `/api/postings` 구조다. 로컬 `.env.local`에는 `BACKEND_URL=http://localhost:8080`이 설정되어 있다. 목록은 기존 정책대로 최근 진행 공고 최대 200개만 가져온다. 상세 `/api/jobs?id=be:공고ID`는 이번 수정부터 목록 캐시와 무관하게 해당 Spring 상세를 직접 조회한다. 백엔드 상세 실패는 502, 잘못된 ID는 400, 없는 공고는 빈 목록이다.

Next.js `/api/skill-categories`는 Spring의 동명 API를 중계한다. 미설정 503, upstream 실패 502이며 임의 예시 데이터로 카테고리 집계를 채우지 않는다. 공고별 문장 분류는 Spring의 전용 API로 제공하며 기존 프론트 차트·LV UI까지 연결한 것은 아니다.

스테이징 사전 점검: 공개 `/api/jobs?limit=24`는 200·총 6개지만 `be:` ID가 없었다. 현재 실제 백엔드 공고 연결이 확인되지 않았다. CD는 웹만 배포하며 Spring을 설치·기동하지 않는다. develop 병합만으로 백엔드 새 JAR가 EC2에 올라간다고 해석하면 안 된다.

웹 서비스가 환경별 설정을 읽도록 배포 스크립트에 선택적 `EnvironmentFile`을 추가했다. 스테이징은 `~/career-data-staging/.env`, 운영은 `~/career-data/.env`를 읽는다. **실제 실행 중인 스테이징 Spring 주소를 확인한 다음** 스테이징 파일에 `BACKEND_URL=...`을 설정하고 웹 서비스를 재시작해야 한다. 저장소에 주소·비밀번호를 추측해서 넣거나 서버 설정을 변경하지 않았다. 운영 main은 이번 반영 대상이 아니다.

## 재현과 검사

분류 파일 갱신이 명시적으로 필요할 때만, 저장된 검토 HTML로 재생성한다. 모델을 호출하지 않는다.

```powershell
python backend/scripts/export_skill_category_snapshot.py path/to/category-browser.html
```

백엔드 `test` 및 `bootJar`, 프론트 `npm run test:api-contract`, `npm run build`로 검증한다. API 계약 검사는 임시 로컬 HTTP 서버를 쓰며 브라우저 설치·공개 API 호출이 필요 없다. CI 프론트 잡에도 계약 검사를 추가했다.
