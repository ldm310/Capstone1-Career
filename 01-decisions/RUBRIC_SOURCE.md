## 2. LV0 · 기본 수행

**정의: 기술이나 방법으로 기본 작업을 구성하고, 실제 수행 결과를 확인한 수준입니다.**

| 기준 ID | 필수 조건 | 확인할 근거 |
| --- | --- | --- |
| `L0-01` | 수행하려는 기본 작업이 식별됨 | 코드·설정·작업 설명에서 입력과 목적 확인 |
| `L0-02` | 해당 작업을 수행하는 구현 또는 설정이 존재함 | 소스 코드, 쿼리, 노트북, 실행 설정 등 |
| `L0-03` | 해당 구현·설정과 연결되는 수행 결과가 존재함 | 버전이 연결된 로그·출력·테스트 결과·분석 산출물 |
| `L0-04` | 결과가 기본 작업의 목적에 부합함 | 단순 프로세스 종료가 아니라 의도한 출력·동작 확인 |

**인정하기 어려운 경우**

- 기술명 나열, 라이브러리 설치·import만 존재
- 실행 명령만 있고 결과가 없음
- 코드는 있으나 실행 가능한지는 확인되지 않음
- 다른 버전의 실행 결과를 현재 코드의 결과로 제시

**직무 예시**

- 백엔드: 간단한 API를 구현하고 요청에 대한 응답 확인
- 데이터: 데이터를 읽어 계산·변환하고 결과 확인
- 배포: 특정 버전을 서버에서 실행하고 의도한 접근·동작 확인

> 예제 기반 수행도 인정할 수 있지만, 사용자의 수행 범위가 확인돼야 합니다. 예제를 활용했다는 이유만으로 불인정하거나 독자 구현으로 과대 인정하지 않습니다.
>

## 3. LV1 · 과제 완성

**정의: 단편적인 기능 실행을 넘어, 구체적인 요구를 입력부터 최종 결과까지 연결한 수준입니다.**

**선행 조건: LV0 필수 조건 충족**

| 기준 ID | 필수 조건 | 확인할 근거 |
| --- | --- | --- |
| `L1-01` | 해결할 요구와 완료 조건이 식별됨 | 요구사항, 이슈, 분석 질문, 인수 조건 |
| `L1-02` | 요구에 대응하는 구현·처리 과정이 연결됨 | 요구–코드·설정·분석 과정의 대응 관계 |
| `L1-03` | 과제의 입력부터 최종 결과까지 흐름이 완성됨 | 기능 연결, 데이터 흐름, 전체 작업 실행 기록 |
| `L1-04` | 완료 조건을 만족한 결과가 확인됨 | 기대 결과와 실제 결과의 비교, 요구별 검증 |

**인정하기 어려운 경우**

- 함수들은 있지만 하나의 과제로 연결되지 않음
- 요구사항과 무관한 기능만 실행됨
- 주요 단계를 수작업으로 대체했으나 그 사실을 숨김
- 화면이나 설명만 있고 실제 처리 결과는 없음

**직무 예시**

- 백엔드: 요청 → 검증 → DB 저장 → 조회 응답까지 요구대로 동작
- 데이터 분석: 분석 질문 → 데이터 처리 → 분석 → 질문에 대응하는 결과 도출
- 데이터 엔지니어링: 원천 데이터 → 변환 → 목적 저장소 적재까지 완료

> 모든 과제에 웹 UI나 DB가 필요한 것은 아닙니다. **그 과제의 완료 조건**을 기준으로 판단합니다.
>

## 4. LV2 · 신뢰성 확보

**정의: 정상적인 입력뿐 아니라 과제에 중요한 제약·예외·실패 조건을 처리하고 검증한 수준입니다.**

**선행 조건: LV1 필수 조건 충족**

| 기준 ID | 필수 조건 | 확인할 근거 |
| --- | --- | --- |
| `L2-01` | 해당 과제의 중요한 위험·제약이 식별됨 | 허용 입력, 권한, 데이터 품질, 실패 영향 등 |
| `L2-02` | 위험·제약에 대한 기대 동작이 정의됨 | 차단·재시도·보류·복구·오류 반환 등의 기준 |
| `L2-03` | 기대 동작을 구현한 처리가 존재함 | 검증 코드, 제약조건, 오류 처리, 데이터 검사 등 |
| `L2-04` | 정상 조건과 중요한 예외·실패 조건을 실제 검증함 | 테스트·실험 입력, 기대 결과, 실제 결과 |
| `L2-05` | 필수 조건을 위반하는 미해결 문제가 없거나, 영향 범위와 처리 방침이 명확함 | 결함 기록, 수정 결과, 제한된 지원 범위 |

**인정하기 어려운 경우**

- 테스트 파일만 있고 실행 결과가 없음
- `try/except`가 있다는 이유만으로 신뢰성을 인정
- 정상 사례만 시험하고 “예외 처리 완료”라고 설명
- 치명적인 데이터 오류나 권한 문제가 확인됐는데 해결·범위 제한 없이 완료로 표시

**직무별 중요한 조건의 예**

| 분야 | 과제에 따라 선택할 검증 항목 |
| --- | --- |
| 백엔드 | 잘못된 입력, 권한, 중복 요청, 트랜잭션 실패, 외부 서비스 오류 |
| 데이터 분석 | 결측·중복, 집계 단위, 시간 범위, 표본 편향, 데이터 누수 |
| 데이터 엔지니어링 | 스키마 변경, 중복 적재, 부분 실패, 재처리, 데이터 정합성 |

**위 항목을 모든 프로젝트에 전부 요구하지는 않습니다.** 직무별 기준표에서 적용 조건과 필수 검증 항목을 사전에 정해야 합니다. 평가기가 결과를 보고 임의로 면제하면 안 됩니다.

## 5. LV3 · 실제 활용·변경 대응

**정의: 결과물이 의도한 환경에서 실제로 활용됐고, 사용 과정의 변경이나 문제에 대응한 수준입니다.**

**선행 조건: LV2 필수 조건 충족**

| 기준 ID | 필수 조건 | 확인할 근거 |
| --- | --- | --- |
| `L3-01` | 실제 활용 대상·환경·목적이 확인됨 | 사용자·내부 소비자·업무 흐름과의 연결 |
| `L3-02` | 단순 배포 완료를 넘어 활용된 기록이 있음 | 사용 로그, 실행 이력, 결과 소비·업무 반영 기록 |
| `L3-03` | 활용 과정에서 발생한 변경 또는 문제가 확인됨 | 이슈, 오류 기록, 요구 변경, 원천 데이터 변경 |
| `L3-04` | 사용자가 해당 변경·문제에 대응한 내용이 확인됨 | 수정 코드·설정·분석과 본인 기여 |
| `L3-05` | 변경을 반영하고 목적에 맞는 동작을 재확인함 | 배포·전달·갱신 기록과 반영 후 검증 |

**인정하기 어려운 경우**

- 배포 URL이나 Dockerfile만 존재
- 실제 사용 없이 접속 테스트만 수행
- “유지보수 담당”이라는 경력 문장만 존재
- 수정 commit은 있지만 어떤 문제에 대응했는지 불명확
- 변경했으나 반영·검증 결과가 없음

**직무 예시**

- 백엔드: 사용 중 발생한 오류를 수정·배포하고 정상화 확인
- 데이터 분석: 실제 사용하던 지표의 정의가 바뀌어 분석을 수정하고 결과 재확인
- 데이터 엔지니어링: 사용 중인 파이프라인의 스키마 변경에 대응하고 적재 결과 검증

> 유료 사용자나 대규모 트래픽은 필수가 아닙니다. 내부 사용자·다른 팀·연동 시스템의 실제 활용도 근거가 될 수 있습니다. 다만 모의실험은 실제 활용으로 바꾸어 표현하지 않습니다.
>

## 6. LV4 · 측정 기반 개선

**정의: 확인된 문제나 한계를 분석하고, 대안을 비교해 적용한 개선 효과와 손익을 검증한 수준입니다.**

**선행 조건: LV3 필수 조건 충족**

| 기준 ID | 필수 조건 | 확인할 근거 |
| --- | --- | --- |
| `L4-01` | 개선 대상과 초기 상태가 측정됨 | 오류율, 품질, 처리 시간, 비용 등 과제 관련 지표 |
| `L4-02` | 문제 원인에 대한 판단 근거가 있음 | 로그 분석, 프로파일링, 데이터 검사, 재현 실험 |
| `L4-03` | 기존 방식과 하나 이상의 실질적 대안을 비교함 | 대안별 조건·결과, 선택 근거 |
| `L4-04` | 선택한 개선을 실제로 적용함 | 변경 코드·설정·처리 과정 및 반영 기록 |
| `L4-05` | 비교 가능한 조건에서 개선 효과를 검증함 | 동일 평가 자료·환경 또는 차이를 통제한 전후 결과 |
| `L4-06` | 부작용·회귀·적용 한계를 확인함 | 다른 지표의 악화 여부, 실패 사례, 효과가 유지되는 범위 |

**인정하기 어려운 경우**

- “빨라졌다”, “정확해졌다”는 주장만 있음
- 변경 전후 데이터나 측정 환경이 달라 효과를 분리할 수 없음
- 여러 설정을 한꺼번에 바꾸고 특정 변경의 효과라고 단정
- 유리한 결과만 제시하고 중요한 품질 저하를 누락
- 비교만 하고 적용 결과는 없음

**직무 예시**

- 백엔드: 병목을 분석해 쿼리·캐시 대안을 비교하고 지연시간 및 정합성 영향 검증
- 데이터: 처리·분석 방법을 비교해 품질이나 효율을 개선하고 결과 왜곡 여부 확인
- 배포·운영: 장애·비용·처리 지연을 분석해 개선하고 운영 결과 비교

## 7. LV5 · 복합 문제 설계

**정의: 서로 충돌하는 요구와 구성요소 간 영향을 고려해 해결 구조를 설계하고, 전체 결과와 실패 조건에서 타당성을 검증한 수준입니다.**

**선행 조건: LV4 필수 조건 충족**

| 기준 ID | 필수 조건 | 확인할 근거 |
| --- | --- | --- |
| `L5-01` | 복수의 요구가 실제로 충돌하며, 그 관계가 설명됨 | 품질–비용, 지연–정합성, 보안–접근성 등 구체적 충돌 |
| `L5-02` | 기존 접근의 구조적 한계가 확인됨 | 측정·실험·운영 기록에 근거한 한계 |
| `L5-03` | 구조적으로 다른 대안과 선택 기준을 비교함 | 구성요소·책임·데이터 흐름·변경 절차의 대안 |
| `L5-04` | 선택한 설계가 구현·적용됨 | 실제 코드·설정·시스템 구성과 전환 기록 |
| `L5-05` | 개별 부분뿐 아니라 전체 목표 충족을 검증함 | 전체 흐름의 품질·성능·보안·정합성 등 관련 검증 |
| `L5-06` | 중요한 실패·부하·변경 조건에서 동작을 검증함 | 과제에 관련된 장애·부하·데이터·환경 변화 시험 |
| `L5-07` | 부작용·잔여 위험·적용 범위와 대응 방침이 확인됨 | 알려진 한계, 복구·철회 방안, 추가 검증 항목 |

**인정하기 어려운 경우**

- 아키텍처 그림만 있고 구현·검증은 없음
- 기술을 많이 사용하거나 마이크로서비스로 나눴다는 사실만 있음
- 프로젝트 규모·직급·팀장 역할을 설계 능력의 증거로 사용
- 개별 성능은 좋아졌지만 전체 결과나 다른 구성요소의 피해는 확인하지 않음
- 팀 설계 성과를 본인의 기여로 입증하지 못함

**직무 예시**

- 백엔드: 지연시간·가용성·정합성 요구의 충돌을 해결하도록 구조를 변경하고 전체 동작·복구 검증
- 데이터: 최신성·정합성·처리 비용 요구를 함께 만족하도록 처리 구조를 설계하고 변경·실패 상황 검증
- 운영: 서비스 중단·데이터 손실·비용 제약을 고려해 배포·복구 구조를 설계하고 검증

## 8. 최종 LV 계산 규칙

현재 초안은 **누적형**으로 정의합니다.

```
LV0: 공통 증거 확인 + L0 필수 조건 전부 충족
LV1: LV0 + L1 필수 조건 전부 충족
LV2: LV1 + L2 필수 조건 전부 충족
LV3: LV2 + L3 필수 조건 전부 충족
LV4: LV3 + L4 필수 조건 전부 충족
LV5: LV4 + L5 필수 조건 전부 충족
```

판정 절차는 다음과 같습니다.

1. 평가할 직무·과제·사용자의 담당 범위를 고정합니다.
2. 기술·과제별 적용 조건을 선택합니다.
3. 근거의 출처·버전·개인 기여·충돌을 확인합니다.
4. 기준별 상태를 판정합니다.
5. **필수·선행 조건이 모두 충족된 최고 LV**를 반환합니다.
6. 미충족·근거 부족·충돌 조건과 추가로 필요한 자료를 함께 표시합니다.

예를 들어 LV2까지 충족하고, LV3의 실제 활용 기록이 부족하다면:

> **확인 LV2 · 신뢰성 확보**
> 
> 
> 주요 예외 검증은 확인됨.
> 
> 실제 활용 기록이 부족해 LV3는 확인하지 못함.
> 
> 별도로 제출된 개선 실험 근거는 보존함.
> 

### 이 누적형의 중요한 한계

**실제 활용 경험이 없으면, 뛰어난 로컬 개선·설계 근거가 있어도 최종 LV는 LV2를 넘지 못합니다.**

이는 오류가 아니라 이 체계가 **‘실제 활용까지 포함한 누적 수행 범위’를 평가하도록 설계됐기 때문**입니다. 따라서 이 결과를 사람의 기술적 잠재력이나 전체 능력의 상한으로 설명해서는 안 됩니다. 이 제한을 팀이 받아들일 수 있는지 확정해야 합니다.

## 9. Rule-based가 담당하는 범위

**최종 LV 계산은 규칙으로 고정할 수 있습니다.** 하지만 자유 형식 원문의 의미를 파악하는 과정까지 이 표만으로 자동 해결되지는 않습니다.

- 규칙으로 검사하기 쉬운 부분: 필수 필드, 버전 연결, 실행 종료 코드, 조건 충족 여부의 조합
- 의미 판단이 필요한 부분: 테스트의 충분성, 원인 분석의 타당성, 대안 비교의 공정성, 본인 기여의 범위

따라서 구조는 다음처럼 잡는 것이 맞습니다.

> **원문 → 기준별 근거 해석·검사 → 조건별 상태 → 공통 규칙 판정기 → LV와 부족한 근거**
> 

**다음 구현에서는 이 표의 기준 ID를 그대로 사용하고, 백엔드·데이터별로 허용 증거와 적용 조건을 추가하면 됩니다. 기존 코드나 기준 파일은 이번 답변에서 변경하지 않았습니다.**
