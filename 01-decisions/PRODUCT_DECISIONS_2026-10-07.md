# Career 최신 대화 결정 및 LV 기준 검토

- 기록일: 2026-10-07 (Asia/Seoul)
- 범위: 이 대화에서 사용자가 갱신한 제품 방향과 평가 기준 논의. 구현 완료 기록이 아니다.
- 기존 문서의 다른 미커밋 변경은 수정하지 않았다. 이 문서는 아래 항목에 대한 최신 대화 기록이며, 다른 문서의 독립적인 정책까지 폐기하지 않는다.
- 상태를 확정 / 제안 / 미정으로 구분한다. 저장 요청을 모든 제안에 대한 승인으로 해석하지 않는다.
- 기존 LV1~3 벤치마크와 결과는 과거 기준의 기록이다. LV0~5로 재검증된 결과가 아니다. 이번 작업은 문서만 저장하며 평가 코드·설정·DB·UI를 변경하지 않는다.

## 1. 확정된 제품 방향

- 대상: 서류 불합격 경험이 있는 신입·주니어 개발자.
- 질문: 다음 채용 기회에 대비해 어떤 역량을 강화하고 무엇을 해야 하는가?
- 기능: 사용자 역량 점검, 채용공고 수집·정형화 및 비교, 스터디 매칭.
- 자기소개서 작성·첨삭은 핵심 범위에서 제외한다. 역량 비교로 불합격 원인이나 합격 가능성을 확정하지 않는다.
- 스터디에서 프로젝트 활동을 통해 역량을 강화한다. 별도 프로젝트 팀 매칭 기능은 확정하지 않았다.

## 2. 확정된 LV 방향과 표시

- 기술별 역량 범위를 기존 LV1~3에서 LV0~5로 변경한다.
- LV0~5의 아래 세부 정의는 현재 검토안이며 검증된 평가 척도가 아니다.
- 근거가 부족한 경우 화면에는 `LV 근거 부족`이라고 표시한다. 이를 LV0이나 능력 없음으로 치환하지 않는다.
- 사용자에게 null을 표시하지 않는 결정과 내부 저장 타입은 별개다. 내부 스키마는 아직 변경하지 않았다.

## 3. 확정된 공고별 스터디 매칭

- 같은 공고에 지원한 사용자들 안에서 매칭한다.
- 해당 공고의 자격요건·우대사항에 관련된 사용자 기술 LV의 단순 평균을 초기 분류에 사용한다. 전체 보유 기술의 평균이 아니다.
- LOW/MIDDLE/HIGH는 해당 공고 맥락의 스터디 참여자 수준이다. 스터디 전체 평균이나 영구적인 사용자 등급이 아니다.
- LOW는 LOW 전용, MIDDLE은 MIDDLE 전용, HIGH는 HIGH 전용 스터디만 신청 가능하다. 다른 등급으로의 신청은 허용하지 않는다.
- 동일 수준 안에서 보완할 기술을 고려한다.
- LOW 커리큘럼은 MIDDLE을, MIDDLE 커리큘럼은 HIGH를 목표로 한다. 다음 등급 스터디에 바로 신청한다는 의미가 아니다.
- HIGH의 세부 학습 목표는 이 대화에서 확정하지 않았다.
- 가중치는 후속 검토 대상으로 두고 초기에는 단순 평균을 사용한다.
- 평균의 L/M/H 경계, 근거 부족 기술의 분모 처리, 최소 평가 범위, 경계값 처리, 재평가 시 이미 참여 중인 스터디 처리는 미정이다.
- 지원 사실 수집·검증 방식은 이 대화에서 최종 확정하지 않았다. 별도 작업 문서의 결정과 통합 시 확인해야 한다.

## 4. 확정된 재평가

- 스터디·프로젝트 종료 후 사용자가 새 결과물을 제출하고 직접 재평가를 요청한다.
- 자료: 변경 코드, 실행·테스트 결과, 문제 해결 설명, 개인 기여.
- 범위: 해당 활동에서 강화하려고 했던 기술.
- 최초 평가와 동일한 LV 기준으로 평가하고 이전·현재 LV, 새 근거, 부족한 근거를 보여준다.
- 과거 결과를 보존하고 새 이력을 추가한다.
- 참여·완료만으로 자동 승급하지 않는다. 근거 부족을 역량 하락으로 표시하지 않는다.
- 확인 가능한 수준 상승과 실제 능력 성장의 인과적 증명을 구분한다.
- 기준 버전이 바뀌었을 때 직접 비교하지 않고 구분하는 방안은 설계 제안이다.
- 자동 GitHub 감지·실시간 평가는 초기 필수 범위가 아니다.

## 5. 역할

- 동민: 프론트엔드 마무리, 사용자 역량 일반화·평가, LLM/Agent 구성 및 LangGraph 도입 검토.
- 승연: 채용공고 수집·정형화, 자격요건·우대사항 추출.
- 선영: 공고·사용자 역량 DB 스키마, 공고별 수준 산정 구조, 지원 사실 수집 방식 검토.

## 6. 사용자 역량 일반화 제안 — 아직 정책 승인·검증 전

사용자 전체를 한 숫자로 평가하지 않고 기술별로 제출 자료에서 확인 가능한 수행 수준을 표현한다. 공고가 바뀌어도 동일한 자료·기준으로 산정한 기술별 LV는 유지하고, 공고에 따라 비교할 기술과 평균만 바꾼다.

자료를 다음 구조로 정리한다:

1. 기술의 표준 이름 및 활용 범위
2. 과제·요구사항
3. 수행 행동과 맥락
4. 실행·검증 결과
5. 결과·한계
6. 개인 기여
7. 원문 위치·자료 버전

사용자 주장 / 코드 존재 / 실행 결과 / 개인 기여를 분리한다. 인용이 실제 존재하는지와 기준을 충분히 뒷받침하는지는 별도로 검사한다.

공통 축: 개념 이해, 구현·적용, 실행·검증, 통합·설계, 분석·개선, 대안·한계 판단. 개인 기여 및 근거 신뢰성을 공통 확인 조건으로 둔다.

기준별 상태 제안: 충족 / 미충족 / 근거 부족 / 자료 충돌. 시스템 실패와 기준 미지원도 역량 판정과 분리한다.

## 7. 현재 LV0~5 검토안

| LV | 공통 정의 | 필수 확인 조건 |
| --- | --- | --- |
| LV0 · 개념 이해 | 기술의 목적과 기본 작동을 이해함 | 핵심 개념을 정확히 설명하고, 간단한 사례의 동작이나 결과를 설명함 |
| LV1 · 기초 사용 | 해당 기술의 기본 기능을 구현하고 실행함 | 기본 구현 코드, 코드와 연결되는 실행 결과, 실행 방법, 핵심 동작 설명 |
| LV2 · 요구사항 적용 | 구체적인 요구사항에 맞게 기능을 구현함 | 요구사항과 구현의 연결, 정상·주요 예외 상황의 검증 결과, 구현 이유 |
| LV3 · 프로젝트 통합 | 다른 구성요소와 연결해 프로젝트 흐름에서 동작하게 함 | 구성요소 간 연결, 전체 흐름 검증, 관련 실패 처리, 설계 선택과 한계 설명 |
| LV4 · 측정 기반 개선 | 확인된 문제를 분석하고 개선 효과를 검증함 | 초기 측정, 원인 분석, 변경 내용, 비교 가능한 전후 평가, 효과와 한계 해석 |
| LV5 · 대안 검증과 설계 | 대안을 검증해 제약에 맞는 설계를 선택함 | 실질적인 대안 비교, 명시적 선택 기준, 선택한 설계의 구현·검증, 여러 관련 조건에서의 효과와 실패 조건 설명 |

## 8. 객관적 검토: 전체 사례 일반화는 아직 불가능

아래 판단은 기준표 구조에 대한 분석이며 실측 정확도가 아니다.

- 공통 설명과 학습 방향으로는 사용할 수 있지만, 이 표만으로 신뢰도·타당성·공정성이 확보되지는 않는다.
- 통합·개선·대안 설계는 항상 누적 순서가 아니다. 독립 SQL 최적화는 통합 없이도 깊은 개선을 보일 수 있고, 신규 설계의 대안 비교에는 기존 시스템 개선 이력이 없을 수 있다. 모든 하위 조건을 무조건 요구하면 과소 인정할 수 있다.
- 기존에 제안한 엄격한 누적 최고 LV 방식은 이 위험을 검토하기 전 확정하지 않는다. 축별 상태를 보존하고 기술별 선행·포함 관계 및 대체 입증 경로를 검토해야 한다. 누적 조건을 임의로 생략해 승급하는 것도 금지한다.
- 큰 시스템의 단순 API 연결과 복잡한 단일 기능 구현을 구분할 과제 복잡도·기여 범위 기준이 없다.
- 코드·실행 자료만으로 독립 수행이나 설명문 이해를 확정할 수 없다. 생성형 AI·튜토리얼·협업 사용 자체를 감점하지 않고 본인의 이해·변경·검증 기여를 확인해야 한다.
- 기술 종류에 따라 실행·검증·실패 처리의 의미가 다르다. 모든 기술에 같은 산출물 형식을 요구하면 누락·편향이 생긴다.
- 문서가 풍부한 사용자와 비공개 업무로 자료를 제출하기 어려운 사용자의 실제 능력 차이를 주장할 수 없다. 보완 자료나 대체 과제 경로는 별도 설계가 필요하다.
- LV0~5는 순서형 범주다. 간격이 같은 수치라는 검증 없이 평균을 실제 능력량이나 채용 확률로 해석하면 안 된다.
- 관련 기술 일부만 확인된 높은 평균은 전체 요구 역량 충족을 뜻하지 않는다. 근거 확보 범위와 기술별 분포를 함께 보여줘야 한다.
- 동일 평균·등급도 개별 기술 수준은 다르므로 수준별 신청 제한만으로 학습 수준 불일치가 해결된다고 보장할 수 없다.

## 9. 검증 및 다음 결정 제안

1. 초기 지원 기술을 명시적으로 제한하고 기술별 기준 ID, 필수 조건, 허용·대체 근거, 불인정 예시, 충돌 처리, 포함 관계를 작성한다.
2. 인접 레벨 경계·상위 축만 강한 사례·실행 기록 누락·개인 기여 불명확·충돌·지원 범위 밖 사례를 포함해 사람이 기준을 시험한다.
3. 검토자 2명이 같은 자료를 독립 판정하고 기준별·최종 LV 불일치와 그 이유를 기록한다. 합의 답안 작성 전 독립 판정 기록을 보존한다.
4. 5~10개 프로젝트로 기준을 조정하고, 이후 30~50개 승인 프로젝트 파일럿을 계획한다. 숫자를 채운 것만으로 모든 기술·사례의 일반화를 입증하지 않는다.
5. 프로젝트 단위로 개발·최종 평가 자료를 분리하고 기준 버전을 고정한다. 반복 실행은 독립 자료 수에 포함하지 않는다.
6. 사람 간 일치도, 모델의 과대·과소 인정, 근거 오류, 보류, 기술별·경계별 오류를 확인한다. 허용 기준은 결과를 보기 전에 팀이 정한다.
7. 그 뒤 동일 기준에서 Rule-only / LLM-only / 고정 워크플로 / Single-agent / Multi-agent를 비교한다. LangGraph는 같은 워크플로의 실행·복구 도구로 별도 비교한다.
- 공급자는 Gemini로 진행한다는 기존 결정이 있다. 특정 구성이나 LangGraph의 우수성은 확정되지 않았다. 키는 이 문서에 기록하지 않는다.

## 10. 변경·대체 관계

| 과거 내용 | 최신 상태 |
| --- | --- |
| 기술 LV1~3 | LV0~5 범위로 변경. 세부 기준은 검토 중 |
| 재평가는 제안 | 사용자 요청형 활동 후 재평가로 확정 |
| L/M/H 대상 불명확 | 공고별 스터디 참여자 수준으로 확정 |
| 전체 기술 평균 가능성 | 공고 자격요건·우대사항 관련 기술 평균 |
| 수준 혼합 매칭 가능성 | 같은 공고·같은 등급 전용 신청 |
| null 화면 표시 | LV 근거 부족으로 표시 |
| 다음 수준 스터디에 즉시 신청 | 현재 수준 전용 스터디에서 다음 수준을 목표로 학습 |
| 모든 하위 조건 누적 인정 제안 | 기술별 포함 관계와 비선형 사례 검토 전 미확정 |

## 11. 참고 근거와 적용 한계

- [SFIA: Levels of responsibility and skills](https://sfia-online.org/en/about-sfia/how-sfia-works): 기술과 자율성·복잡도·영향 등의 책임 수준을 구분하는 다차원 구조 참고. Career LV와 직접 대응하거나 검증해 주는 기준은 아니다.
- [AERA: Testing Standards briefing](https://www.aera.net/portals/38/docs/outreach/standards_hill_briefing_slides_final.pdf?timestamp=1410876719244): 사용 전 타당성 근거 수집과 운영 중 추가 검증 원칙 참고. Career 평가기가 해당 표준을 충족했다는 의미가 아니다.

이 문서의 저장은 정책 구현·DB 저장·벤치마크 재실행을 의미하지 않는다.
