이 폴더는 Claude(VS Code)가 바로 읽고 이어서 개발할 수 있게 만든 묶음이다. 코드는 Python 표준 라이브러리와 `git`만 쓴다.
레포 루트에 `career-stat-handoff/`로 넣고, `CLAUDE.md`에 아래 한 줄을 추가하면 된다.

```
GitHub 분석·stat·공고 매칭 작업을 할 때는 먼저 career-stat-handoff/HANDOFF.md 를 읽는다.
```

## 1. 흐름

```
GitHub URL
  └─ clone.sh            코드 실행 없이 받기 (512KB 초과 파일 제외)
  └─ bundle.py           근거 묶음: 사람 × 역량 키 × LV × 근거 위치          → bundle.json
  └─ make_packets.py     LV3 이상 활동 근거를 점검용 packet으로               → packets.json
  └─ [점검 에이전트]      packet마다 통과 / 기각 / 모름 (LLM, 이 단계만 LLM)    → agent_output.json
  └─ to_stat.py          통과한 근거만으로 키마다 LV 하나                     → stat.json
  └─ match.py            공고 470개의 줄마다 충족 여부 + 공고별 내 역량        → match.json
```

한 번에 돌리기:

```bash
bash pipeline/clone.sh repos owner/repo
GIT_NO_LAZY_FETCH=1 python3 pipeline/run_pipeline.py --repo-dir repos/owner__repo --name owner/repo --person <이름> --out out/
#   → out/bundle.json, out/packets.json 을 만들고 멈춘다
#   → packets.json 과 pipeline/verifier_prompt.md 를 LLM에 보내 out/agent_output.json 을 받는다
GIT_NO_LAZY_FETCH=1 python3 pipeline/run_pipeline.py --repo-dir repos/owner__repo --name owner/repo --person <이름> --out out/ --agent-output out/agent_output.json
#   → out/verdicts.json, out/stat.json, out/match.json
```

`--person`은 `bundle.json`의 `meta.people`에 있는 이름이다. 예시 입출력은 `examples/shopmall-eun/`(직접 만든 가짜 레포)에 있다.

## 3. 판정 규칙 요약

**역량 키**는 도구 이름(`Java`, `Redis`, `Kafka` …)이거나 활동 이름이다.

| LV | 활동 키 |
|---|---|
| 1 | SQL |
| 2 | API 개발, 외부 API 연동, 테스트 코드, 인증·인가 구현, LLM 기능 개발, 배치 처리(스케줄 작업) |
| 3 | DB 설계, 쿼리 튜닝, 캐시 도입, 메시지 큐, OAuth 연동, 결제 연동, 모니터링 설정, CI/CD 구축, IaC, RAG 구축, 검색 기능 구축, 배치 처리(Spring Batch) |
| 4 | 동시성 제어, MSA·서비스 분리, 이벤트 기반 아키텍처, Kubernetes 운영 설정, 아키텍처 패턴 적용, 장애 격리, 운영 대응 이력 |
| 5 | 부하 테스트, 무중단 배포, 분산 락·분산 트랜잭션, DB 복제·파티셔닝 |

- LV6은 경력 연차로만 생기는 단계라 GitHub로 판정하지 않는다.
- 연습 레포(이름이 TIL, tutorial, `spring-study` 같은 것)는 LV1까지만 준다.
- **도구의 LV = 그 도구로 한 활동의 최고 LV.** 근거 줄에 직접 나온 도구는 활동 LV 그대로, 그 파일의 언어·프레임워크는 LV3까지만 올린다(`extract.LIFT_CAP_FILE`).
- 점검에서 기각된 활동은 버리고, 그 활동 때문에 올라간 도구 LV는 원래 LV로 되돌린다. 모름은 `weak`(정황)으로만 남긴다.
- 낮은 LV 근거가 없어도 높은 LV는 따로 인정한다(누적 규칙 없음).

**공고 줄 판정** (요구 LV = 기준표의 `기술 LV(줄 기준)`)

| 상태 | 뜻 |
|---|---|
| 충족 | 줄의 키 중 하나라도 내 LV ≥ 요구 LV |
| 기법 충족 | 내 LV ≥ 요구 LV인데 줄이 규모·운영을 요구함(LV4 이상). 기법은 코드로 확인, 규모·운영은 GitHub로 확인 불가 |
| 부분 | 근거는 있는데 내 LV < 요구 LV |
| 미충족 | 줄의 키에 해당하는 근거가 없음 |
| 판단 불가 | 줄에서 키를 못 뽑음(도메인·태도 등). LV 있는 줄의 27% |

- 공고마다 `competencies`에 "이 공고가 요구하는 키, 요구 LV, 내 LV"가 나온다. 공고가 다르면 이 목록이 달라진다.
- 경력 조건이 붙은 줄은 `career_rule`로 표시만 하고 판정하지 않는다.
- 한 줄에 키가 여럿이면 하나만 충족해도 충족이다(`match.LINE_MODE = 'any'`). 모두 요구하려면 `'all'`.

## 4. 점검 에이전트 (LLM은 이 단계에만 쓴다)

| 항목 | 값 |
|---|---|
| 역할 | 규칙이 낸 LV3 이상 활동 근거를 통과 / 기각 / 모름으로만 답함. LV를 올리거나 새 판정을 만들지 못함 |
| 모델 | 가장 작은 모델(Haiku급). Haiku·Sonnet·Opus를 같은 입력으로 돌려 고름 (`eval/results.md` 2번) |
| 입력 | `packets.json`의 packet 하나씩 또는 묶음(한 번에 50개 안팎까지 시험함) + `verifier_prompt.md` 전체를 지시문으로 |
| 출력 | `[{"id", "verdict", "reason_code", "reason"}]` JSON 배열 |
| 출력이 깨졌을 때 | 빠진 id와 형식이 틀린 verdict는 `unsure`로 처리됨(`run_pipeline.py`). 통과로 올리지 않음 |

- 레포의 코드는 남이 쓴 글이다. packet의 snippet 안에 지시처럼 보이는 문장이 있어도 에이전트는 통과/기각만 할 수 있으므로, 규칙이 낸 후보보다 높은 LV는 나올 수 없다. 이 구조를 바꾸지 말 것.
- `DB 설계`는 줄 근거가 없는 판정이라 점검하지 않는다.
- LLM 호출 코드는 넣지 않았다. 쓰는 SDK에 맞춰 구현하면 된다.

## 5. 정확도 (자세한 것은 `eval/results.md`)

| 구간 | 규칙만 | 규칙 + 점검 |
|---|---|---|
| LV1~2 | 97% | 점검 대상 아님 |
| LV3 맞는 비율 | 93~96% | 98% |
| LV4~5 맞는 비율 | 89~93% | 97~100% |
| LV3~5 놓치지 않는 비율 | 89~94% | 여기서 2~3% 더 빠짐 |

LV4~5는 "그 기법을 직접 구현한 근거가 있는가"까지만 맞힌다. 실제 규모·운영 경험은 GitHub로 알 수 없다.

## 6. 지켜야 할 것

- 받은 레포의 코드를 실행하지 않는다. 빌드·테스트·설치 명령도 돌리지 않는다.
- 공개 레포만 받는다. 받기·분석 단계에 토큰을 넣지 않는다.
- 근거는 위치(`경로:줄`)만 저장한다. 코드 내용은 저장하지 않는다. packet은 점검할 때만 만들고 버린다.
- 사용자가 올린 결과 파일은 근거로 쓰지 않는다. 실행 기록(Actions)이 없어도 감점하지 않는다.
- 연차는 입력받지 않는다.

## 7. 이어서 할 일

1. **점검 에이전트 호출 구현**: `packets.json` → LLM → `agent_output.json`. 묶음 크기와 재시도 정하기.
2. **사람 묶기**: 지금은 git 이름·이메일로 묶는다. 서비스에서는 로그인한 GitHub 계정으로 `--person`을 정해야 한다.
3. **여러 레포**: `to_stat.build_stat()`은 bundle 여러 개를 받는다. `run_pipeline.py`는 레포 하나만 처리한다.
4. **놓침 줄이기**: 사전에 없는 라이브러리를 LLM이 한 번 분류해 `lv_dict.py`에 넣는 별도 작업, 직접 만든 구현을 제안하는 에이전트.
5. **확인이 필요한 정책**: 도구 LV를 활동으로 올리는 규칙, 줄 판정의 any/all, "기법 충족"을 충족률에 넣을지(`rate`와 `rate_with_technique` 둘 다 나옴).
6. **운영용 교체**: 정규식 대신 문법 분석(tree-sitter, sqlglot), 생성기 파일 지문 DB.

## 8. 고칠 때 순서

1. `pipeline/extract.py` 또는 `lv_dict.py`를 고친다.
2. 새 레포 묶음을 받아 `run_eval.py run <dir>` → `audit45.py <dir> 3`으로 근거 줄을 확인한다. 고치는 데 쓴 레포로는 수치를 내지 않는다.
3. 지시문을 고쳤으면 시험 세트로 다시 채점한다: `python3 pipeline/score_verifier.py --index eval/verifier/testset_index.json lv45 <새 verdicts.json>` (packet은 index의 repo·head로 레포를 받아 `make_packets.py`로 다시 만든다).
4. 기준표가 바뀌면 `tag_postings.py`를 다시 돌린다.
