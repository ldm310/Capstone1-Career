# LV 계산 규칙 — 7개 카테고리 (2026-11-24)

> 손 메모 두 번째 이미지의 방식(개수 → 단계 → 평균)을 모든 카테고리에 똑같이 씀. 백엔드만 점수형이며 자세한 기준은 `backend-lv-v5-6vars-final-2026-11-24.md`.
> 단계 시작값 · 가점 0.5 · 유통기한 1달은 임시값이며 8명 테스트로 맞춤.

## 공통 규칙
1. 개수 변수 → 단계(그 단계 시작값 이상이면 그 단계, 0~5) → 카테고리 LV = 단계 평균(소수 첫째 자리). 예: Java 커밋 120개 3단계 · 바꾼 줄 8,000줄 4단계 · 기간 90일 3단계 → (3 + 4 + 3) ÷ 3 = 3.3
2. 선행조건 없음. T/F 변수는 가점: T면 카테고리 LV +0.5(최대 5.0), F면 그대로.
3. 개수 가점(부가 기술 수, 검증된 AI PR 수): 단계로 바꿔 평균을 올릴 때만 넣음.
4. 모름(탐지 규칙이 없는 언어·스택)은 평균에서 뺌. 모든 변수가 모름이면 판정 불가.
5. 레포는 모두 합쳐서 셈. 개수는 레포 합계(커밋 수 포함)이고 같은 것은 한 번. 각 변수는 그 카테고리 파일을 바꾼 내 커밋·내 줄만 셈.
6. 기간
   - 유통기한 1달(프로그래밍 활용 · 데이터 엔지니어 · 데이터베이스): 그 카테고리의 내 커밋 날짜를 순서대로 놓고 30일 넘게 비면 끊음 → 구간마다 첫날~마지막 날을 양 끝 포함해 세고(혼자 떨어진 커밋은 1일) 모두 더함. 예: 1/1 · 1/20 · 2/10 · 6/1 · 6/15 → 41일 + 15일 = 56일. 쉬는 기간(방학·시험)을 경험 기간으로 세지 않으려는 것.
   - Actions(운영 배포): 레포별 GitHub Actions 첫 실행일 ~ 마지막 커밋일, 유통기한 없음. 예: 3/1 ~ 8/31 = 184일.
7. 중복은 한 번만: Airflow는 DAG 수에서만 셈 · 주 DB로 쓴 DB는 데이터베이스 부가 기술에서 뺌 · 백엔드 안에서 캐시는 API 변수의 캐시 가점에서만 셈.
8. 기술을 썼다고 보는 기준(T/F 변수 · 부가 기술 공통): 내 코드에서 실제로 호출한 곳 1곳 이상, 또는 설정 파일에 그 기능이 쓰이도록 적혀 있음(주석 · 끄는 값 · 예시 파일이면 X). 의존성 파일이나 import 줄에만 있으면 X. 프레임워크는 그 프레임워크로 해당 카테고리 게이트를 통과한 레포가 있어야 함.
9. 공고에 따라 달라지는 것(공고 DB 사용, 공고에 적힌 부가 기술 중 몇 개)은 공고와 맞출 때만 씀. 공고 없이 보여 주는 LV에는 안 넣음.
