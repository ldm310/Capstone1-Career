## A-1. 백엔드 밖 6개 + 기술 기록

### 공통 약속(A1~A7이 같이 씀)

1. 단계 [7c-1]: 계산은 본문 10.1, 설정 파일은 본문 10.8이다. 시작값은 「사용자 결정(2026-11-26)」으로 확정한 고정 사다리다. 사람 값과 상관없이 정했고, 데이터로 시작값을 정하던 방식(값이 있는 사람의 분위수 등)은 쓰지 않는다. 기간은 모두 일수다. 값이 시작값 이상이면 그 단계다(1단계 시작값 미만은 0단계).

   | 변수 | 1/2/3/4/5단계 시작값 |
   |---|---|
   | 프로그래밍 커밋 수 | 1 / 7 / 30 / 180 / 365 |
   | 프로그래밍 바꾼 줄 수 | 1 / 200 / 1,000 / 5,000 / 25,000 |
   | 프로그래밍 기간(일) | 1 / 7 / 30 / 150 / 300 |
   | 배포한 레포 수 | 1 / 2 / 3 / 5 / 8 |
   | 배포 평균 기간(일) | 1 / 7 / 50 / 150 / 250 |
   | DAG 수 | 1 / 2 / 5 / 10 / 20 |
   | 데이터 엔지니어 기간(일) | 1 / 7 / 30 / 100 / 250 |
   | 설계 테이블 수 | 1 / 3 / 8 / 20 / 50 |
   | DB 기간(일) | 1 / 7 / 30 / 120 / 250 |
   | API 연동 수 | 1 / 3 / 10 / 30 / 100 |
   | 데이터 송수신 | 1 / 3 / 10 / 30 / 100 |
   | 이벤트 처리 | 1 / 10 / 30 / 100 / 300 |
   | AI 기술 다섯 변수 | 「문서」 값 그대로(A6) |
   | 개수 가점 재료(부가 기술 수·백엔드 부가 영역 수) | 목록 크기에 맞춤(아래 '개수 가점 단계'). 검증된 AI PR 수는 「문서」 1/2/5/12/30 그대로 |

   - 명세 예 [7c-1](커밋 120개 · 8,000줄 · 90일)은 이 사다리로 3 / 4 / 3단계 = 3.3이다.
   - 개수 가점 단계(「사용자 결정(2026-11-26)」 B-85 닫힘): 시작값은 목록 크기에 맞춘다. 목록을 다 쓰면 5단계다. 「제안」 계산: 단계 = 쓴 개수 ÷ 목록 크기 × 5를 반올림(0.5는 올림, 아래 결정 예와 맞춤), 1개 이상이면 최소 1단계. 2단계에서 돌린 1/2/3/4/5(「Claude 임시값」)는 쓰지 않는다.

     | 목록 | 크기 | 쓴 개수 → 단계 |
     |---|---|---|
     | 데이터 엔지니어 부가 기술(Spark·Kafka·dbt·Databricks·Snowflake·BigQuery·Iceberg·Hadoop) | 8 | 1·2개 1 · 3개 2 · 4·5개 3 · 6·7개 4 · 8개 5 |
     | 백엔드 부가 영역(파일 저장소·실시간 통신·API 문서·소셜 로그인) | 4 | 1개 1 · 2개 3 · 3개 4 · 4개 5(2단계는 없음) |
     | 데이터베이스 부가 기술(MongoDB·Elasticsearch·Redis + '그 밖의 DB' 1칸, 「제안」) | 4 | 백엔드 부가 영역과 같음 |
     | 검증된 AI PR 수 | 목록 아님 | 「문서」 1/2/5/12/30 |

     - 데이터베이스 목록은 '주 DB 말고 더 쓴 DB'가 열려 있어서 이름 있는 3개 + '그 밖의 DB' 1칸 = 4로 본다(「제안」). '그 밖의 DB'는 몇 종류를 써도 1칸이다(「제안」).
2. 가점 [7c-2·3]: 「사용자 결정(2026-11-26)」 명세 방식이다. T/F 재료는 T면 +0.5(결과는 최대 5.0). 개수 가점 재료(부가 기술 수·검증된 AI PR 수·백엔드 부가 영역 수)는 단계로 바꿔 평균에 한 항으로 넣었을 때 평균이 오를 때만 넣는다. 계산 세부는 본문 10.7이다. 카테고리마다 적은 '가점 재료'가 그 목록이다.
   - 결과에는 가점 넣은 LV와 함께 가점 없는 LV와 가점 재료(T/F 결과·개수)를 같이 보인다(「제안」).
   - 「사용자 결정(2026-11-26)」 B-84 닫힘: 단계가 모두 0인 카테고리에는 T 가점과 개수 가점 둘 다 없다(LV 0 그대로). 가점 재료(T/F·개수)는 결과에 그대로 보인다(「제안」). 2단계에서는 이 규칙이 없어 P06 프론트가 0→0.5, P11 AI가 0→1.0이 됐다. 개수 가점 시작값은 공통 약속 1의 '개수 가점 단계'다.
3. 카테고리 파일 [7c-5]: 각 변수는 그 카테고리 파일을 바꾼 내 커밋·내 줄만 센다. 문서에는 언어 말고 카테고리 파일 목록이 없다. 카테고리마다 「제안」 목록과 판정 방법을 본문 9.7에 모았다(「미정」 [B-23]).
4. 기간(유통기한 1달) [7c-6]: 규칙·예·경계(「제안」 [B-18])는 본문 10.3, 날짜 종류와 시간대는 본문 9.3이다.
5. 값 상태(본문 6.3) 쓰는 법:
   - 모든 변수는 원값·단계와 함께 값 상태를 보인다.
   - 0(안 씀)은 규칙이 있는 스택에서 흔적도 없을 때 쓴다. 흔적이 전혀 없는 0은 LLM에 보내지 않는다(「사용자 결정(2026-11-26)」. 2단계 표본 66건 중 '예'는 간접 1건이었다).
   - 흔적(의존성·설정·규칙 없는 스택 코드)은 있는데 규칙이 못 뽑으면 S5로 보낸다. 3번 실패하면 모름(3번 실패)이고 로그에 남긴다. S5를 돌리지 않으면(`--llm off`, 잔액 부족, 사용자가 준 안전선) 대기로 남는다(본문 6.3).
   - 본인 것이 아닌 부분(공통 약속 12)을 빼서 0이 되면 '안 씀'(흔적 없음)이다. '모름'이 아니다(「제안」).
   - 모름(「사용자 결정(2026-11-26)」 B-55 닫힘): 확인된 것만 세고 '모름 n개'를 붙인다. 모름을 0으로 보지 않는다. 대상이 모두 모름일 때만 변수가 모름이다(「제안」). 백엔드는 모름인 항목만 만점에서 뺀다([AI 확인] 항목이 3번 실패해 모름이어도 같음, A-2.4·A-2.9). 레포를 못 받으면 '못 본 레포'로 표시하고 나머지로 잰다(「제안」). GitHub 조회가 실패하면 0으로 보지 않고 '확인 못 함'으로 두고 3번까지 다시 묻는다(「제안」, 2단계에서 레포가 소리 없이 빠진 버그. 본문 7장).
   - README 주장만 있음·PaaS 대행 표시 [BE-11·12]를 이 부록 카테고리에도 쓴다(「제안」 [B-59]). 해당 없음은 백엔드 1점 항목에만 있다. 해당 없음의 범위(문서 괄호가 예시인지 전체 목록인지)는 「미정」 [B-56](사용자 설명 대기)이고, 그동안 A-2.4 규칙 4의 「제안」을 기본값으로 쓴다.
   - 카테고리의 모든 변수가 모름이면 판정 불가다. 판정 불가는 0이 아니라 빈 값으로 넘긴다.
6. 썼다고 보는 기준 [7c-8]은 A7에서 기술마다 한 번 판정한다. T/F 재료·부가 기술·기술 기록이 그 결과를 같이 읽는다.
7. 근거 다시 확인 5가지는 본문 13.6을 그대로 쓴다. 쿼리 API 인자로 쓰인 SQL·JPQL 문자열을 '실제 코드'로 보는 예외, 설정 줄·commit·pr 근거의 확인도 거기에 있다.
8. 노트북(.ipynb): 본문 9.5(「제안」 [B-21]). 근거 위치는 '경로#셀:줄'로 적는다.
9. 프로젝트(「제안」 [B-22]): 첫 커밋이 같은 레포나 내 커밋 SHA가 겹치는 레포(포크·미러·사본)는 한 프로젝트(사본 묶음)로 본다. '같은 것은 한 번'을 가리는 키에 이 프로젝트를 쓴다. 남기는 레포는 ① 같은 SHA를 처음 가진 원본 ② 내 커밋이 가장 많은 레포 순이다(「제안」, 공통 약속 13).
10. 겹침 기본값(「제안」 [B-60]): [7c-7]의 세 예는 모두 한 카테고리 안의 중복이다. 그래서 카테고리가 다르면 같은 근거를 따로 쓰고, 결과에 '같은 근거'를 표시한다. 공고 문장에 카테고리가 여럿 붙을 때의 처리는 S8에서 정한다.
11. S5를 많이 부를 변수: AI 기법·기능 수(늘), 데이터 송수신(자주), API 연동 수(주소·테이블을 못 푼 호출), DB 깊이 5단계(규칙으로 못 정한 목록 API, 튜닝 종류마다 '필요한 곳에 다 했는지' 확인), 규칙 없는 스택의 백엔드 게이트(레포마다 한 번), 백엔드 '애매함' 사례, 강의 레포 판정(후보 레포마다 한 번), 팩토리 DAG·규칙 밖 ORM(드묾). 프로그래밍 활용과 운영 배포 기간은 git만으로 재므로 LLM을 부르지 않는다(실패하면 도구로만 다시 시도. 결정 ④를 좁혀 읽은 「제안」 [B-08]). 부르기 전에 예상 금액을 알린다(「사용자 결정(2026-11-25)」).
12. 본인 것이 아닌 부분 빼기(「사용자 결정(2026-11-26)」 원칙: 자기가 한 부분이 아니면 뺀다). S3가 파일 판(blob)과 커밋마다 제외 표시(복사본·통째 올림·수업 따라 치기·문제 풀이·대회 제공 파일)를 남기고, 모든 변수는 이 표시만 보고 뺀다. 변수마다 따로 거르지 않는다(「제안」).
    - R1 같은 내용 파일: 한 사람의 모든 레포에서 내용이 같은 파일(blob SHA 같음)은 가장 먼저 들어온 하나만 센다.
    - R2 통째 올림: 한 커밋이 새 코드 파일 10개 이상 · 새 줄 300 이상 · 그 레포 내 줄의 30% 이상을 만들고 그 뒤 내가 다시 고치지 않은 것(「Claude 임시값」. 근거: 새 파일을 만든 내 커밋 2,500개의 분포와 진짜 프로젝트 오탐). 연습·강의 레포와 사본에 쓴다(사용자 결정).
    - R5 보통 레포의 대량 업로드(「사용자 결정(2026-11-26)」 B-16 닫힘): 보통 레포에서 R2 꼴(한 번에 올린 커밋, 숫자는 R2와 같은 「Claude 임시값」)이 만든 파일은 '내 것'이라는 근거가 있을 때만 센다. 근거가 없으면 뺀다. 근거 예(사용자 결정): 올린 뒤 그 파일을 내가 계속 고쳤다(그 뒤 내 커밋이 그 파일을 다시 바꿈). 「제안」: 몇 번 고쳐야 '계속'인지는 그 뒤 내 커밋 1개 이상(R2의 '다시 고치지 않은 것'의 반대)으로 둔다. 그 밖의 근거로 내 다른 레포에 같은 파일이 조금씩 쌓인 기록이 있음(같은 경로·비슷한 내용을 여러 내 커밋이 만듦)도 인정한다. 결과에 R5로 뺀 파일·줄과 인정한 근거를 레포마다 보인다.
    - R5 영향(2단계 추정, 다시 재야 함): A안의 R2에도 '이후 안 고침' 조건이 있으므로 '고친 근거'만 보는 규칙은 R2를 모든 레포에 쓴 값(연습 레포 분석의 A안)과 거의 같다. 그 값은 P03 73%, P04 54%, P10 57%의 줄이 빠졌고(R1·R3까지 넣은 몫. R2를 연습·강의 레포에만 쓰면 29%·0%·31%), 다른 곳에서 만든 자기 프로젝트를 한 번에 옮겨 올린 레포가 통째로 빠지는 오탐이 있었다. 「제안」 근거(내 다른 레포의 기록)가 이 오탐을 얼마나 살리는지는 새 코드로 다시 잰다.
    - R3 강의 레포에서 한 번 쓰고 안 고친 파일은 뺀다. 두 커밋 이상에서 고친 파일과 과제·복습·미니 프로젝트 커밋이 만든 파일은 남긴다(「제안」). 수업 시간에 따라 친 코드는 모두 뺀다(사용자 결정).
    - R4 알고리즘 문제 풀이: 커밋 수에서만 빼고 바꾼 줄·기간에는 넣는다(사용자 결정).
    - 강의 레포 판정: 후보는 도구로 고른다(수업 기록 메시지 30% · 문제 풀이 꼴 커밋 50% · 템플릿 · README 낱말 · 레포 이름. 숫자는 「Claude 임시값」이고 후보 고르기에만 쓴다). 확정은 LLM이 넷 중 하나로 한다: 남의 강의 따라 침 / 본인 자료 / 부트캠프 사본 / 해당 없음(「LLM 추출」). 본인 자료면 보통 레포로 보고 R1만 쓴다. 부트캠프 사본은 공개 원본이 있으면 원본의 내 커밋으로 세고, 없으면 뺀다(사용자 결정).
    - 대회 노트북·레포: 대회가 준 파일(베이스라인·제출 양식·대회 소개)을 빼고, 본인이 고치거나 새로 쓴 부분만 센다(사용자 결정).
    - 변수마다 쓰는 법(「제안」): 커밋 수는 빠지지 않은 줄을 하나 이상 바꾼 내 커밋만 센다. 바꾼 줄은 빠지지 않은 줄만 센다(사용자 결정 '내가 직접 한 부분만'). 기간은 센 커밋의 날짜만 쓴다. 테이블·DAG·API 연동·데이터 송수신·이벤트·AI 근거·DB 깊이 근거는 그 정의 줄·호출 줄이 빠진 파일에 있으면 뺀다. 백엔드 비율 항목은 빠진 파일의 API를 분자·분모 둘 다에서 뺀다. 운영 배포는 빠진 파일에만 배포 근거가 있으면 '배포한 레포'로 세지 않는다.
    - 「제안」(확인 전): 베이스라인을 닮았지만 이름이 다른 파일처럼 애매한 것은 LLM이 가린다. 본인 것이 아닌 파일만 만든 커밋은 커밋 수·기간에서도 뺀다. 판정은 그 커밋의 diff 기준이다.
    - 결과에 레포마다 뺀 줄·커밋·근거 수와 이유를 보인다(점수에는 넣지 않음, 「제안」).
13. 레포 범위(「사용자 결정(2026-11-26)」): 본인이 커밋한 모든 공개 레포(팀·조직·남의 레포, 1~3커밋 오픈소스 수정 포함)를 본다. 분석 브랜치는 기본·develop·dev 그대로이고, 본인 GitHub 계정 커밋만 센다. 모든 변수가 이 범위로 잰다.
    - 큰 레포: 레포 전체 크기가 400MB(「Claude 임시값」)를 넘으면 빼지 않고, 필요한 파일만 받는 방식(blob:none)으로 받은 뒤 내 커밋이 바꾼 파일만 받는다(사용자 결정. 2단계 실측: 3.4GB 레포가 63초·309MB). 그래서 큰 레포도 다른 레포와 같은 변수를 잰다.
    - 「제안」: 기여 레포 찾기(GraphQL 기여 기록·커밋 검색·소속), 포크·미러는 내 커밋 SHA로 묶어 한 번만(공통 약속 9), 병합 커밋(부모 둘 이상)은 커밋 수·줄·기간에서 뺌, 빈 레포는 분석 브랜치의 커밋 수로 판정, 다시 쓰는 clone은 끝 SHA를 GitHub와 비교. 2단계에서는 이 수집 버그로 P01 소유 레포 4개, P07 2개가 빠졌다.
    - 남의 레포의 시작일 문제(운영 배포 기간)는 A2, '내 API' 기준은 A-2.1이다.
14. 쏠림 표시(「사용자 결정(2026-11-26)」): 단계 변수 중 레포마다 더해지는 값에서, 공통 약속 12를 적용한 뒤에도 4단계 이상(「Claude 임시값」)이고 그 값의 80% 이상이 레포 하나에서 나온 칸만 사람이 확인할 목록에 올린다. 자동으로 빼지는 않는다. 2단계 값으로는 16칸이다.
    - 2단계에서 이 표시가 잡은 부풀림 두 가지는 표시와 별개로 생성·외부 파일 거름 목록(본문 9.6)에 넣는다: dbt 컴파일 결과 폴더(`dbt_target/compiled` 등, P17 SQL 줄), 레포에 넣은 외부 라이브러리 폴더(`tmp/…/python-libs` 꼴, P18 C·Python 줄).
15. 정의 파일(「제안」, 프론트는 「사용자 결정(2026-11-26)」): 변수 정의는 한 파일에만 두고, 규칙·LLM 질문 틀·보고서가 그 파일을 읽는다. 실행 기록(`run.json`)에 정의 파일의 판과 sha256을 남기고, 정의가 바뀌면 그 정의로 받은 캐시 답을 다시 쓰지 않는다. 2단계에서는 규칙·질문 틀·정의 기록이 서로 달랐다(A5). 질문 틀 안에 정의 문장을 직접 쓰면 실패하는 시험을 둔다(「제안」).
16. 「제안」을 구현하는 법(「사용자 결정(2026-11-26)」): 이 부록의 「제안」은 기본값으로 구현한다. 「미정」으로 남은 곳도 거기 적힌 「제안」이 기본값이다. 정의 파일(공통 약속 15)의 각 정의에 출처(`문서`·`사용자 결정`·`제안`·`Claude 임시값`)를 적고, 그 정의로 낸 값 옆에 결과 화면 표시를 단다. 사용자가 나중에 바꾸면 정의·설정 판만 올린다(코드를 고치지 않음).
    - 표시 자리: result.json(값마다 `basis` 칸, 「제안」 이름), report.md, 팀 화면 미리보기의 값 옆.
    - 표시 말(「제안」 목록, 팀 확인 항목): '제안 기준'(「제안」 정의로 낸 값) · 'LLM 추출'(S5가 뽑은 값) · 'LLM 판정'(규칙이 없는 스택의 백엔드 게이트, A-2.1) · '모름 n개'(공통 약속 5) · '애매함'(규칙이 표시해 S5로 보낸 백엔드 경계 사례, A-2.2) · 'Claude 임시값'(숫자 기준).
    - 한 값이 「제안」 정의 여러 개를 거쳤으면 '제안 기준'을 한 번만 달고, 거친 정의 ID 목록은 result.json에만 둔다(「제안」).

### A1. 프로그래밍 활용(언어마다)

#### 계산

- 「문서」[7c-표·설명]: 언어마다 LV = (커밋 수 단계 + 바꾼 줄 수 단계 + 기간 단계) ÷ 3이다. 관련 코드가 T면 +0.5(최대 5.0)이다(명세 방식, 공통 약속 2). 공고가 언어를 정하면 그 언어 LV, 아니면 가장 높은 언어 LV를 쓴다. 예 [7c-1]: 커밋 120개 3단계 · 8,000줄 4단계 · 90일 3단계 → 3.3.
- 단계 시작값은 고정 사다리(공통 약속 1)이고, 위 예를 그대로 지킨다(3 / 4 / 3단계).
- 표시: 언어마다 한 줄(원값·단계·가점 없는 LV·관련 코드 T/F·가점 넣은 LV, 뺀 커밋·줄 수와 이유)을 낸다. 대표 LV는 가장 높은 언어 LV이고, 언어 이름을 같이 보인다. '공고가 정한 언어'는 S8이 고른다.
- 가점 재료: 관련 코드 T/F.
- git 기록만으로 잰다. LLM이 할 일이 없어서 S5에서 LLM을 부르지 않는다. 받기·읽기 실패는 도구로만 다시 시도한다(최대 3번, 「제안」 [B-08]). 다만 제외 표시(공통 약속 12)에 드는 강의 레포 판정은 S3 단계에서 LLM이 한 번 하고, 그 결과를 여기서도 쓴다.

N+1 해결은 그 한 종류이고, 연관 데이터를 쓰는 목록 API의 절반 이상에서 N+1이 없을 때 인정한다. 다른 튜닝(실행 계획 확인·배치 조회·페이지 나누기 최적화 등)도 근거로 인정한다. 어느 종류든 필요한 곳에 다 했는지를 LLM이 확인한다(한 줄로 5단계가 되지 않음). 판정 방법은 아래 '5단계 판정'. 커밋 메시지의 '성능 개선' 같은 글은 후보 찾기에만 쓴다 [BE-11] | 규칙으로 못 정한 목록 API(호출을 못 따라감, 연관 데이터를 쓰는지 애매함, Prisma '행마다 쿼리 없음', 규칙 밖 ORM), 다른 튜닝 종류의 '필요한 곳'과 '다 했는지' 확인 |

**5단계 판정**(「사용자 결정(2026-11-26)」 두 번의 구현, 방법은 「제안」)

5단계 = 쿼리 튜닝 전체다(두 번째 결정). 종류마다 따로 판정하고, 한 종류라도 통과하면 5단계다(「제안」). 모든 종류에 같은 틀을 쓴다: 규칙이 '그 튜닝이 필요한 곳'(분모)과 '한 곳'(분자)을 고르고, LLM이 필요한 곳에 다 했는지 확인한다 [AI 확인]. 근거 줄은 내 줄이고 빠진 파일(공통 약속 12)은 쓰지 않는다. 근거 1곳 원칙(1~4단계)과 근거 파일 수 기록은 그대로다.

| 종류 | 필요한 곳(분모) | 한 곳(분자) | 출처 |
|---|---|---|---|
| N+1 해결 | 연관 데이터를 쓰는 내 목록 API | 그 API의 쿼리에 [BE-DB표] N+1 해결이 붙음 | 「사용자 결정(2026-11-26)」 첫 번째. 세부는 아래 1~6 |
| 배치 조회 | 「제안」 반복문 안에서 행·id마다 조회·저장하던(또는 그렇게 해야 했던) 내 코드 | 「제안」 묶어서 한 번에 부름(IN 조회·`findAllById`·`bulk_create`·`saveAll` 배치 설정·`createMany` 등) | 종류는 사용자 결정, 분모·분자는 「제안」 |
| 페이지 나누기 최적화 | 「제안」 페이지를 나누는 내 목록 API 중 큰 표를 읽는 것(API6과 같은 단위. '큰 표'인지는 LLM이 스키마·쿼리를 보고 판정) | 「제안」 offset 대신 커서·키셋 페이지, 전체 개수 쿼리를 따로 가볍게 만듦 | 〃 |
| 실행 계획 확인 | 「제안」 조인·정렬·검색이 있는 내 무거운 쿼리(LLM이 고름) | 「제안」 실행 계획을 본 근거(EXPLAIN을 부르는 내 코드·시험·스크립트, 또는 실행 계획 결과를 커밋 메시지·PR 설명·같은 커밋 문서에 적음. 글 근거는 본문 13.6 doc 근거와 같게 확인)가 있고, 같은 커밋·PR이나 바로 뒤 내 커밋에서 그 쿼리·인덱스를 고침. 바꾼 코드 없이 글(주장)만 있으면 X [BE-11] | 〃 |
| 그 밖의 튜닝 | 「제안」 LLM이 종류를 이름 붙여 분모·분자를 같이 낸다. 결과에 '그 밖'으로 보인다 | 〃 | 「제안」('등'의 구현) |

- 통과(「제안」): 종류마다 분자 × 2 ≥ 분모(N+1과 같은 '절반 이상'). 분모가 1~3개여도 비율만 본다(N+1의 사용자 결정을 다른 종류에도 씀). LLM이 '필요한 곳에 다 했다'고 확인해야 통과다. 분모를 규칙으로 못 정한 종류(실행 계획·그 밖)는 LLM이 분모·분자를 같이 내고, 프로그램이 근거 줄을 다시 확인한다(본문 13.6).
- 분모 0(연관 데이터를 쓰는 목록 API 없음): N+1 종류는 '판정 대상 없음'이다(사용자 결정). 「제안」(기본값): 다른 종류는 따로 판정한다. 첫 번째 결정의 '분모 0이면 4단계까지'와 두 번째 결정의 '다른 튜닝도 근거'가 이 경우에 부딪쳐서, 두 번째 결정을 따른 읽기다(재승인 때 확인).
- 첫 번째 묶음의 '나중에 건 인덱스·eager 설정은 튜닝 의도가 확실하지 않다'(2단계 Claude 정의)는 이 결정으로 바뀐다. 나중에 건 인덱스는 실행 계획 확인과 이어질 때만 「제안」 근거가 된다. 인덱스만이면 3단계다.

N+1 해결 종류의 세부(「사용자 결정(2026-11-26)」 첫 번째의 구현):
1. 분모: 연관 데이터를 쓰는 내 목록 API. 목록 API는 백엔드 API6(목록 나눠 보내기)과 같은 단위다(여러 건을 돌려주는 GET: List·Page·QuerySet·배열 반환, DRF ListAPIView·ViewSet list, GraphQL 목록 리졸버). '내 API'는 그 API 코드의 과반이 내 줄인 것(A-2.1)이고, 빠진 파일(공통 약속 12)의 API는 넣지 않는다. 응답을 만들 때 연관 엔티티의 값을 읽으면 '연관 데이터를 쓴다'(DTO 변환 안의 `order.getMember().getName()`, 중첩 serializer, `source='rel.x'`, 응답 모델의 relationship 필드). 연관 필드가 없는 목록은 분모에서 뺀다.
2. 분자: 그 API가 쓰는 쿼리에 [BE-DB표]의 N+1 해결이 붙어 있는 것. 처리 함수 → 서비스 → 리포지토리·쿼리를 파서로 따라가 찾는다(인터페이스는 구현까지). 같은 레포 어딘가에 해결 한 줄이 있는 것으로는 안 된다. 행마다 리포지토리를 부르는 반복문이 있거나 해결 없이 지연 로딩 연관을 읽으면 'N+1 있음'이다.
3. 「제안」(확인 전): 전역 설정(`default_batch_fetch_size`)은 그 레포의 목록 API를 모두 해결로 본다. 연관 열을 조인해 한 번에 고르는 DTO 조회도 해결로 본다.
4. S5 [AI 확인]: 규칙으로 못 정한 목록 API와, 규칙이 통과로 본 경우의 '필요한 곳에 다 했는지' 확인을 보낸다(처리 함수·쿼리·엔티티. 두 번째 결정: 어느 근거든 LLM이 확인). 답은 예·아니오·모름과 근거 줄이고, 프로그램이 근거 줄을 다시 확인한다(본문 13.6). 3번 실패면 그 API는 모름이다. [AI 확인] 처리는 A-2.9와 같다(B안으로 넣고 사람 판정 표본을 모음).
5. 계산: 모든 레포를 합쳐 분자 × 2 ≥ 분모면 N+1 종류 통과(5단계)다. 목록 API 수에 따로 문턱을 두지 않고 비율만 본다(1~3개여도 같음, 사용자 결정). 결과에 분모를 표시한다. 모름 API는 분자·분모에서 빼고 수를 적는다. 「제안」(확인 전): 모름이 판정된 것보다 많으면 그 종류를 '모름'으로 둔다. 모든 종류가 통과 못 함·모름이면 깊이는 확인된 가장 높은 단계(4 이하)이고, 모름인 종류 수를 붙인다(공통 약속 5).
6. 분모 0(연관 데이터를 쓰는 목록 API가 없음): N+1 종류는 '5단계 판정 대상 없음'이다(사용자 결정). 다른 종류는 위 표대로 따로 판정한다(「제안」, 위 '분모 0'). 근거는 A4 카테고리 파일(본문 9.7)의 내 줄에서만 찾는다.
- 2단계 추정(N+1 종류만, 호출을 따라가지 않은 상한, 확인 못 함. 다른 종류는 재지 않음, N/A): 이 판정으로 P01·P02는 5→4, P07은 4→5가 될 가능성이 있다. 5단계 근거가 사본·수업 코드에만 있던 P09·P10·P12는 공통 약속 12로 먼저 빠진다.

- 「제안」(정의 파일 초안에 적을 것): 서버에 안 가는 SDK 동작(로그인 상태 듣기·세션 읽기·공개 주소 만들기·authStore 비우기), 정적 파일(.json 등) 요청, WebSocket·SSE·Realtime 구독, 목·시험·스토리북·생성물·주석 처리된 코드, 의존성에만 있고 내 줄에 호출이 없는 SDK는 세지 않는다. 내 줄 = 호출 줄이나 주소·테이블을 정한 줄이 지금 남은 내 줄이다.
- 「제안」 대응표 예: PocketBase `getList`·`getFullList`·`getFirstListItem` → 목록 읽기 1, `getOne` → 한 건 읽기, `create`·`update`·`delete` → POST·PATCH·DELETE, `authWith*` → 각각 1. Supabase `select`는 `.single()`이 있어도 읽기 1(쿼리는 경로 틀에서 빼므로). 20명 중 쓴 사람이 없는 BaaS(Amplify·Appwrite 등)의 표는 비워 두고 판을 올릴 때 사용자에게 보인다.

- 기록에만 쓰는 기술(가점 재료가 아닌 것)은 S5를 부르지 않고 '흔적만'으로 둔다. 공고 대조(S8)에 그 기술이 나올 때만 S5로 보낸다(비용). 변수 뽑기 결정 ④는 LV 변수에 대한 것으로 읽었다. 결정 ④를 좁혀 읽는 것이므로 사용자 확인이 필요하다 「미정」 [B-08].

#### 다른 카테고리와 겹침

- 판정 기준이 T/F 재료·부가 기술과 같으므로([7c-8]) 기술마다 한 번 판정하고, A1~A6 가점 재료·백엔드 부가 기술 영역·S8이 같이 읽는다. Redis처럼 여러 카테고리에 걸리는 기술도 기록은 하나다.
- LV 밖이라 다른 변수와 근거를 같이 써도 된다.

- 상한은 변수 LV를 1~2로 묶으므로 오탐 비용이 크다. 스파이크에서 단순 흐름 규칙은 비밀번호 저장 흐름을 9레포 중 3레포에서 틀렸다(다른 파일에서 저장, 해시와 평문을 함께 저장. 조사 점검, 사람 판정 아님).
- 그래서 규칙이 흐름을 끝까지 잇고 근거 줄이 '근거 다시 확인 5가지'(본문 13.6)를 통과한 '확실'일 때만 건다.
- 애매하면 '확인 필요'로 S5에 넘긴다. LLM이 '예'로 답하고 근거 확인을 통과하면 「LLM 추출」로 건다(「사용자 결정(2026-11-25)」: LLM 값은 처음부터 LV에).
- 3번 실패면 걸지 않는다. 대신 로그와 결과에 '상한 확인 못 함'을 남긴다.
- 「미정」 [B-52] 레포마다 다른 상한 실수가 있어 깨끗한 레포가 하나도 남지 않을 때 어느 상한을 걸지(「제안」 레포마다 걸린 상한 중 가장 느슨한 값. 규칙 14의 '가장 좋은 결과'와 맞춤)

2. '글 비밀번호로만 막는 API'를 따로 가리는 규칙은 두지 않는다(「사용자 결정(2026-11-26)」: 프로젝트에 필요 없음). 2단계에서 그렇게 분류된 3곳은 모두 잘못 분류였다. 셋 다 로그인 사용자 비교(로그인 ID = 요청 ID)를 먼저 한 뒤 비밀번호를 한 번 더 확인하는 API였는데, 규칙이 비밀번호 비교 줄만 봤다. 그래서 분모에 남기는 안·빼는 안을 설정으로 두지 않는다.
3. 요청에 대상 번호(URL·본문·쿼리)가 없고 서버가 로그인 사용자의 것만 찾아 고치는 API(예: 내 알림 모두 읽음, 내 오늘 목록 저장)는 분자·분모 모두에서 뺀다(「사용자 결정(2026-11-25)」).
4. 「제안」(확인 전): 로그인 사용자와 비교하지 않는 수정·삭제 API는 따로 빼지 않고 '본인 확인 없음'으로 분모에 남긴다(비밀번호만 확인하는 경우도 같다). '로그인 ID = 요청 ID' 비교(principal 비교 등)도 본인 확인으로 인정한다.

규칙(S4, 「제안」):
1. 라우트 표에서 대상 API를 고르고, 대상 번호가 오는 곳(경로 변수·쿼리·본문 필드)을 찾는다. 경로 변수만 보면 틀린다(A-2.6).
2. 핸들러가 고치는 자원 모델에 작성자·소유자 칸이 있는지, 관리자 전용(경로·역할 검사)인지 본다.
3. 호출 그래프를 따라 인정 모양 ①~⑤를 찾는다. 비밀번호 비교 줄만 보고 판정하지 않는다(2단계 잘못 분류). 로그인 사용자 값이 어느 인자로 넘어가는지 같이 따라간다.
4. 규칙만으로 확정하는 것: (작성자 자원, 확인 있음) → 분자. (대상 번호 없음·관리자 전용·작성자 없음, 확인 없음) → 분모에서 뺌.
5. S5로 보내는 것: 규칙은 '뺌'으로 봤는데 확인 코드가 있음(충돌) · 작성자 자원인데 확인을 못 찾음 · 자원 판정이 애매함.

S5(LLM, [AI 확인]):
- 처음 보내는 것: API 정의, 핸들러, 따라간 함수, 가드, 자원 모델(원래 줄 번호). 더 필요하면 LLM이 읽기 전용 도구로 가져온다(본문 13.3). 남이 쓴 함수도 판정 재료로는 보내지만, 근거로는 내 줄만 받는다.
- 답 칸(submit_answer의 value): `kind`(owned·self·admin·none·unclear) · `target_in`(path·query·body·none) · `owner_check`(yes·no·unclear) · `shape`(①~⑤·other·none). 근거·이유는 submit_answer 공통 칸(`evidence`·`reason`, 본문 13.5)이다.
- 확정 조건: `kind`가 admin·none이면 확정(분모에서 뺌). self는 `target_in` = none일 때만 확정(분모에서 뺌). owned이고 `owner_check`가 yes·no면 확정. 그 밖은 다시 본다(최대 3번).
- 3번 실패: 그 API는 모름(3번 실패)이다. 분자·분모에서 빼고 모름 API 수를 항목에 남긴다(「사용자 결정(2026-11-26)」 B-55: 확인된 것만 세고 '모름 n개'). 모든 대상이 모름이면 SEC4가 모름이고 만점에서 뺀다.
- 받아들이기: `owner_check` = yes의 근거 줄은 근거 다시 확인 5가지(내 줄 포함, 본문 13.6)를 통과해야 한다. 통과 못 하면 그 회차 답을 버리고 다시 본다.
